### Signals Router → Cloud SQL + `/similar` Endpoint
- **Files**: `platform/api/routers/signals.py`, `docs/GCP_IMPLEMENTATION_STATUS.md`
- **What Changed**: Signals router primary path is now Cloud SQL. `_query_signals_sql()` runs `SELECT COUNT(*)` (cheap on the `(ticker, entry_time)` index) plus a windowed `SELECT ... LIMIT :limit` against `historical_signals`, projecting/aliasing columns to the response schema the frontend already expects (`time`, `direction`, `close`, `rsi`, `ema9`, `ema20`, `volume`, `score`, `conditions_met`, `return_pct`). Direction, min_score, and `end_date` (+ optional `end_time`) all push down to the WHERE clause. The old GCS parquet path is renamed `_load_ticker_df_parquet` and kept as a fallback for local-dev shells where `CLOUD_SQL_CONNECTION_NAME`/`DB_USER`/`DB_PASS`/`DB_NAME` aren't set; selection between paths happens once at module import. New endpoint `GET /api/signals/{ticker}/similar?direction&rsi&score&rsi_band&limit`: bucketises by direction + score + RSI (±band), pulls matching prior bars, and computes aggregate stats (count, mean/median/p25/p75 MFE pct, mean return at 5/20 min, pct profitable, earliest/latest). Used by the Charts page Similar Setups card to surface every prior occurrence of the same setup.
- **Why**: Old reader cached the entire signals parquet (hundreds of MB) per ticker with a 1-hour TTL — first request after eviction stalled while the parquet downloaded and parsed. Cloud SQL with the existing index serves the same response in sub-100ms regardless of how much history exists. The `/similar` endpoint had no equivalent on the parquet path; it relies on `WHERE rsi BETWEEN ... AND signal_strength = ...` server-side, which is impractical to push through the cached-DataFrame pattern (filter would walk every row in Python on every call).
- **Benefit**: Page load no longer pays the cold-start parquet cost. The Similar Setups feature becomes feasible — frontend posts the live bar's RSI + score + direction and gets a stats summary back fast enough to update on every voter fire.

### `historical_signals` Bulk Insert ~100× Throughput
- **Files**: `gcp/historical_signals.py`, `scripts/backfill_historical_signals.sh`
- **What Changed**: `bulk_insert()` no longer relies on pg8000's executemany (which serialises one `INSERT ... VALUES (:p1, :p2, ...)` statement per row). It now builds a single multi-row form per chunk: `INSERT INTO historical_signals (...) VALUES (:p0_col1, ..., :p0_colN), (:p1_col1, ..., :p1_colN), ... ON CONFLICT (ticker, entry_time) DO NOTHING`. Per-row parameter names are unique (`p0_*`, `p1_*`, ...) so SQLAlchemy binds them as a single batch. Default `chunk_size` lowered from 5000 to 1000 because Postgres caps bind parameters at 65535 and the table has 23 columns — 1000 rows × 23 = 23K params, well under the limit but with headroom for any future column additions. NaN/Inf scalars from pandas are still mapped to `None` in the same loop. New `scripts/backfill_historical_signals.sh` walks `[ticker × calendar month]` calling `run_historical_signals.py` once per `(symbol, month)` so MarketAnalyzer.add_technical_indicators (which loads the entire range into one DataFrame) only sees ~30k bars per call. Greps the worker logs for the meaningful info lines so the bash output stays scannable.
- **Why**: The 11-year backfill for IWM/QQQ/SPY requires writing several million rows; at 6 rows/sec it would take ~9 hours per ticker and contend with everyone else's writes. Profiling pointed at the wire-format overhead, not the indicator math. Monthly chunking matters because `add_technical_indicators` allocates an O(n) DataFrame for the whole period; loading 11 years at once would peak above the worker's RAM.
- **Benefit**: Backfill goes from ~9 hours/ticker to under 10 minutes; resume-safe; bounded memory regardless of total date range.

### Cap Earnings-Ticker Fan-out at Top-25 by Tier + Market Cap
- **Files**: `gcp/fetchers/fetch_market_data.py`, `gcp/premarket_brief.py`, `docs/GCP_IMPLEMENTATION_GUIDE.md`
- **What Changed**: `_earnings_tickers_in_window()` (the daily fetcher's earnings-window resolver) now ranks tickers by `optionable DESC, market_cap DESC NULLS LAST, ticker` and limits to a configurable `top_n` (default 25). `load_earnings_for_brief()` does the parallel work for the Discord embed: pulls `market_cap` from `earnings_calendar`, picks the largest non-null cap across the ticker's source rows (UW omits market_cap; we don't want a NULL from one source to outrank a real value from another), sorts by `(date, tier, -market_cap, ticker)`, then caps at `top_n=25` (overridable via `BRIEF_MAX_EARNINGS` env var). Both call sites accept `top_n=0` for the legacy unbounded behaviour. The fetcher's `--max-earnings-tickers` flag and the brief's env var default to the same number so the morning embed surfaces the same names the daily fetcher actually backfills bars for. GCP_IMPLEMENTATION_GUIDE §10 Pre-Market Brief flow updated to document the earnings query, the tier+market_cap sort, and the `top_n` cap.
- **Why**: AlphaVantage allows 150 req/min on the current tier; each ticker costs ~3 calls (intraday + daily + supporting). The full earnings calendar can return 200+ tickers, so a thin earnings week was eating the minute budget before the loop reached IWM/QQQ/SPY — those silently skipped with empty AV responses, leaving the four core tickers stale for ~2 weeks before anyone noticed. The cap stays well under the budget; ranking by has_options + market_cap means the names that are dropped are illiquid, non-optionable junk, not the AVGO-tier ones traders actually care about.
- **Benefit**: Core tickers stay current. The premarket Discord embed and the daily Cloud Run fetcher now name the same tickers, so traders can trust that any earnings name in the brief actually has fresh bars in Cloud SQL.
