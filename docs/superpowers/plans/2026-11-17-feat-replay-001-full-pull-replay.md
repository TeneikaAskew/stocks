# Full-pull replay into a separate store (SPY, QQQ, IWM): implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
> Every task cites a spec section and the done_when item it advances. done_when items are named D1 to D11 as the spec's frontmatter names them; the map below gives each its task.

**Goal:** Pull SPY, QQQ and IWM 1-minute bars through the nightly's own `fetch_month` into a schema `replay` keyed by run, apply the live data fixes there, run the brief and the insight on that store as if live, and compare bars, flags, premarket, triggers, stops, targets and the insight plan with what was published, writing nothing outside schema `replay`.

**Architecture:** `gcp/replay_store.py` owns the run context (`REPLAY_RUN_ID`), the table map, a statement classifier and a fence that wraps every DBAPI connection made while a run is set, so a write naming a table outside schema `replay` raises `ReplayWriteRefused` before it reaches the driver. `gcp/replay_full_pull.py` is the entry (`pull`, `fix`, `compare`, `drop`); `gcp/replay_compare.py` holds the comparers. The brief and the insight keep their code paths and switch three things under a run: where the session premarket and level basis are read from, which tables they write, and that they post nothing.

**Tech Stack:** Python 3.12, pandas, SQLAlchemy 2 over pg8000 (`gcp.database`), psycopg2 or pg8000 through `lib.agents.model_routing.connect()`, google-cloud-storage, pytest (`monkeypatch`, `caplog`), Postgres 15 with pgvector in CI's `integration-tests` job (`.github/workflows/backtest-pipeline.yml:90-163`).

**Spec:** docs/superpowers/specs/2026-11-17-feat-replay-001-full-pull-replay-r2.md (r2: approved under the owner's direction of 2026-11-17, "Overcome all blockers"; it supersedes `docs/superpowers/specs/2026-11-17-feat-replay-001-full-pull-replay.md`, approved through stocks #2054, and declares `site_source_notes: [LIVE-08]`). The r2 spec folds in the three gaps #2077 left for this plan and the plan's other spec points; its section "Changes from r1" lists them as (a) to (g). This plan lands after the r2 spec PR merges. Read it on `origin/main` 9d862b05c: every code line number below is that commit's, and is unchanged on 379ad19d0.

## Review Focus

Inputs the spec implies and no done_when test pins, most likely first. Each has a test in the task that owns the code.

- **A broad handler swallows a refusal.** `bulk_copy_upsert` falls back to `upsert_dataframe` on any exception (`gcp/database.py:884-889`), the brief marks a ticker `PLAYBOOK_FAILED` on any `persist_level_map` exception (`gcp/premarket_brief.py:1795-1818`), `_calibrate_on_demand` returns the unavailable state on any exception (`lib/agents/summarizers.py:547-565`), and `_run_scheduled` exits 0 with failed tickers (`gcp/insight_pipeline_job.py:964-975`). Under a run each re-raises `ReplayWriteRefused` and a replay batch with a failed ticker exits 1. Tasks 4, 8, 10.
- **A replay started without its clock or outside its run.** `REPLAY_RUN_ID` with no `BRIEF_AS_OF`, with `--post-existing` or `BRIEF_PREMARKET_FROM_BARS=true`; an insight with no instant, in on-demand child mode (`INSIGHT_RUN_ID`), or for a ticker outside the run: each exits 2 before any read. Tasks 8, 10.
- **No premarket row versus no premarket bars.** A session whose pull holds no premarket bar gets a `replay.premarket` row with status `no_premarket_bars` and the brief builds as live does with no premarket; a missing row (fix not run) raises `ReplayRowMissing` and the run exits 1. Tasks 7, 8.
- **A pull run again after a partial failure.** The same run id and parameters pull only the months with no `success` row, write no second object, and converge; other parameters exit 1. Task 5.
- **The insight reads a basis built after its instant.** If the run's canonical `replay.premarket_analysis` row was rebuilt by a late replay brief (cutoff at or after the insight's `as_of`), the insight exits 1 rather than read it. Task 10.

## Capacity (CLAUDE.md Rule 0; spec Capacity), copied into the PR body and re-measured in Task 13

At 364 bytes a row with indexes (SPY partition 911,327,232 bytes over 2,503,499 rows, `db-query-w4l46`): the week (October whole plus the November pull of 31,219 rows) is about 92,700 rows and 34 MB; a year, 14 months, about 860,000 rows and 313 MB a run. Premarket rows: 3 a session a ticker, about 2,270 a year. Brief and insight rows: as live (3 a session).
- **Velocity:** vendor calls one a ticker-month: the week 2 x 3 = 6, a year 14 x 3 = 42, 2015 onward 144 x 3 = 432. Bar writes: one transaction a ticker-month, inserts in chunks of 5,000 (about 5 statements, about 210 a year). Fix: one daily read and one coverage read a ticker, one bar read a ticker and target month (its read window, about 1.4 months), one flag write a ticker and month, one published-row read and one as-read listing a ticker-session. Brief: one run a session; insight: one run a ticker-session; compare: two reads a family and ticker-month. Pinned by the I/O shape tests of Tasks 5, 6, 7, 11 and 12.
- **Wall-clock:** vendor 0.69 to 0.86 s a call (measured 2026-11-17), so a year's pull is under a minute and the history about 6 minutes against 150 calls a minute. Bar writes at 0.5 to 2 s a statement: the week about 30 statements, under a minute; a year about 210, 2 to 7 minutes. Brief 28 to 110 s a run (2026-11-13 to 11-16): the week 3 to 11 minutes; a year 252 runs, 2 to 8 hours in sequence, striped over 10 Cloud Run tasks under an hour. Insight 32 to 72 s a ticker: the week 18 runs, 10 to 22 minutes; a year 756 runs, striped over 20 tasks under an hour. Task timeout at 4x the measured run, set by FEAT-DEPLOY-001.

## Choices this plan makes where the spec leaves one open (each reported to the owner with the plan)

1. **#2077 gap 1:** no fan-out under a run (table above).
2. **#2077 gap 2:** full-pass flags kept by the cut pass's judged mask; publication by the live coverage's judged range (table above).
3. **#2077 gap 3:** every replay unique and conflict target starts with `replay_run_id` (table above).
4. **The body for sha256 and the object.** `fetch_month` gains one keyword-only argument, `on_response: Optional[Callable[[dict, bytes], None]] = None`, called once with the parameters as sent without the key and the body, after `raise_for_status` and before parsing. With None, the request, the logs and the return are unchanged; `process_symbol` and `replace_month` pass nothing. The observer adds no log line and the error log at `:184` keeps its text: the key that log can carry is #2085, outside this plan. The alternative, reading the body by patching `requests.get` in production code, was not taken.
5. **Run id:** `^[a-z][a-z0-9-]{2,56}$`, so `triggered_by 'replay:<R>'` fits `VARCHAR(64)` (`premarket_analysis_history.triggered_by`, `insight_reports_history.triggered_by`) and the id is a safe bucket path segment.
6. **The fence is installed only on connections made while a run is set**: in the Cloud SQL branch's `_getconn` (`gcp/database.py:162-169`), through a `creator` in the direct `DB_HOST` branch (`:119-138`), and in `model_routing.connect()` (`lib/agents/model_routing.py:76-99`). A fenced connection keeps the run id it was made with.
7. **`gcp/replay_store.py` is registered in `REPLAY_PATH`** with `("*",)`: it is the one module that reads `REPLAY_RUN_ID`, and `registration_offenders` fails any file that reads a `REPLAY`-shaped env var without a registration (executed on a synthetic source, 2026-11-17). Every other module asks `replay_store.current_run()`.
8. **Bucket adapter:** `replay_store.ReplayBucket` over `google.cloud.storage`, writing only under `replay/v1/` and reading only under `replay/v1/` and `premarket-as-read/v1/`. `export_intraday_bars.GcsBucket` cannot be imported (`test_nothing_in_the_tree_reads_the_copy`).
9. **The pull's month write:** `replace_rows_in_window(df, 'replay.intraday_bars', {'replay_run_id': R, 'ticker': T, 'interval': '1min'}, 'ts', start, end, chunksize=5000)` over the Eastern calendar month (`eastern_bounds_utc(first_day, time(0), time(0))[0]` of the month and of the next), one transaction. A rerun pulls only months with no `success` row. An object is written only for a `success` body, once (`if_generation_match=0`).
10. **Prior inputs:** for every read kind, the stored `close`, `open`, `atr_14`, `atr_5` of the last `market_data_daily` row before the session with a close (the refresh's rule, `gcp/fetchers/fetch_premarket_refresh.py:139-169`), from one bounded read a ticker, recorded on the row (Decision 5). The filter: the level parameters in force on the session through `premarket_filter_inputs` (Decision 6); tests may pass a recorded filter through `premarket_snapshot`'s `recorded_filter`, which is how D5's values were measured.
11. **Which slot a published row or an object is:** by the Eastern time of its basis `premarket.fetched_at` (object: its name's instant): before 09:20 the early refresh, at or after 09:20 the late. An object is the slot's when its instant equals the published basis's `fetched_at`; with none recorded, the latest object of the slot before 08:30 (early) or 09:30 (late). `refresh_0920` rows are written only where a late published row or a 09:20 object exists. Read 2026-11-17 (`db-query-cx5lg`): the late slot first applied on 2026-11-17 (`LATE_SLOT_APPLIED`, written 14:22:11Z), so 2026-11-09 to 11-16 have no `refresh_0920` row; the first as-read objects are 2026-11-17's, their instants equal to the published bases' `fetched_at`.
12. **Published insight:** the latest `insight_reports_history` row with `run_kind 'scheduled'` written before 09:30 ET for the ticker and session. Read 2026-11-17: each of 2026-11-16 and 11-17 holds an `auto_refresh` report at 08:11 ET (`cron:auto-refresh-top-n`) and a `scheduled` one at 08:46 ET.
13. **Price equality:** bars at `PRICE_TOLERANCE`; premarket values, triggers, stops, targets and insight prices by `price_cents`; persona `rationale` is LLM text and not compared.
14. **Run kinds:** the canonical replay rows say `replay` (as `BRIEF_AS_OF` and `INSIGHT_AS_OF` already stamp them); history rows keep `_resolve_run_kind_and_update`'s `replay_refresh`; `triggered_by` is `replay:<R>` on both.
15. **Insight tickers under a run:** `INSIGHT_TICKERS` when set, else the run's tickers from `replay.runs`; a ticker outside the run exits 2.
16. **The role grants** are committed as `gcp/queries/replay_role_grants.sql` (role `replay_writer`: USAGE and SELECT on schema `public`, USAGE and SELECT, INSERT, UPDATE, DELETE on schema `replay`, and `ALTER DEFAULT PRIVILEGES` for later replay tables), applied by the integration test and, on the owner's yes, in production.
