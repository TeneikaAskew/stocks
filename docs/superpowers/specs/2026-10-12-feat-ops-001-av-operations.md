# Make AV audit completeness and field coverage observable

## Authorization and intake

This records the scope of the six-stage remediation plan presented after the live AV/GCP audit and authorized by the user on 2026-10-12: "Proceed with the plan, executing inn parallel". Execution method: parallel isolated worktrees, one author and PR per capability. Capability: FEAT-OPS-001; matching catalog row in docs/product/02-FEATURE-CATALOG.md. The listed issues are touched, not claimed closed without their own acceptance evidence.

## Problem

audit-infra-drift cannot list scheduler jobs but exits zero and reports no findings. Strict freshness can pass unknown check results, and several reads swallow database errors. Required adjusted-close/AV-indicator fields have no complete coverage check.

## Non-goals

No expansion to all 128 APIs, change to strategy/model promotion or risk calibration, fabricated financial values, blind rewrite of historical timestamps, unrelated IAM/audience changes, or unbounded backfill. API failures and historical-only exclusions remain explicit.

## Approaches considered

1. Targeted contract repair, independent reviewed streams, bounded source-backed repair and selective deployment — chosen to preserve the verified working paths.
2. Replace the complete ingestion platform — excessive scope and operational risk.
3. Change schedules without repairing data contracts — leaves the demonstrated corruption and observability gaps.

### Audit outcomes and strict queries

Infrastructure checks that cannot execute are incomplete, not a no-findings success. Exit 2 for incomplete checks or failed alert delivery; ordinary completed drift findings retain exit 0 to avoid treating a detected drift item as an execution error. Use strict SQL with explicit server-side timeouts in every freshness query path currently capable of swallowing database failures. Emit an attributable unknown check on a database error; do not silently skip a required missing table, column or result. Strict freshness exits 2 whenever any unknown result, any incomplete required result, required prerequisite skip, or an empty report exists, even when aggregate display status is warn or stale; disabled/planned/unconfigured required indicator and registry checks are normalized to unknown with an explicit prerequisite reason, never a successful skipped check. An optional baseline check intentionally outside its own applicability window retains existing display compatibility but cannot substitute for required AV coverage; otherwise stale exits 1 and a completed non-stale report exits 0. Preserve existing aggregate display semantics for callers. No new overlapping UI freshness implementation.

### Durable compute and bounded interactive snapshot reads

The existing cold/expired API claimant executes audit_all inline. Moving that audit to an API background thread is insufficient: platform/deploy.sh configures request CPU throttling and min-instances=0, so work after a response has no durable execution guarantee. Keep the existing API lifecycle and move all complete freshness computation to the existing scheduled freshness-watchdog Cloud Run JOB. Full-mode invocations publish the complete shared audit result after computation into a bounded durable snapshot; API processes neither import the audit/calendar module nor run/schedule an audit, background worker, vendor request or Cloud Run job. AV-only invocations must not replace the complete snapshot with a partial AV report. This adds no recurring job, always-on API instance or idle CPU commitment.

OPS owns an additive singleton schema block: `ops_freshness_snapshots(snapshot_key TEXT PRIMARY KEY CHECK(snapshot_key='full'),producer_generation_seq BIGINT,report JSONB,report_bytes INTEGER,report_row_count INTEGER,completed_at TIMESTAMPTZ,producer_execution TEXT,code_revision TEXT,last_error_at TIMESTAMPTZ,error_class TEXT)`. CHECK constraints cap report_bytes at2097152 and report_row_count at4096; actual deterministic UTF-8 JSON serialization is checked before publication and must agree with the stored metadata. The full producer_generation_seq is copied from the compact running claim's globally increasing generation_seq, not its per-scope/window claim_seq; the SQL update rejects an older generation even when its completion clock is later. This remains ordered when windows/scope hashes change. A ready report requires aware completion time, reviewed code revision and actual producer identity. Publish the entire snapshot/metadata atomically after the full audit completes, using completion time rather than audit-start time; concurrent producers cannot replace a newer completed snapshot with an older one. A failed audit/publication records a bounded error state without advancing completed_at or erasing an existing last good report. A later success clears the error only when it genuinely supersedes it. Database write failure emits attributable incomplete telemetry and nonzero exit. No snapshot is published as healthy if checks were unknown, stale or partial: those statuses remain intact in the shared evaluator's report.

`platform/api/routers/health.py::freshness_report_dict` reads only this indexed singleton through a strict bounded read with an actual whole-read wall-clock allowance<=0.5seconds including pool/connect/network; statement_timeout alone is insufficient. Reuse one in-process immutable report/expiry tuple and nonblocking single-flight for the small snapshot read, never for audit execution. Cold/expired-cache claimants finish within one second; concurrent decliners return a stale cached report immediately or typed503 if none exists. Snapshot age is measured from its producer completion time: age>300seconds is explicitly stale, and repeated DB reads never refresh that age. A latest error newer than the last good completion remains explicit stale/unavailable rather than resetting a healthy cache. Missing schema/record or an unavailable bounded-read provider returns typed503; unexpected defects remain typed500 with safe error classes. No infrastructure/exception text appears in the response. If the deployed driver cannot bound its cold read, refuse activation and return503 rather than execute an unbounded fallback. The local300second read lease applies to successes and bounded failures/no-snapshot states: negative state is cached explicitly until the lease expires, so repeated cold failures cannot create unbounded per-request SQL attempts. The cached error never claims a successful report. Both freshness and admin routes consume exactly this shared snapshot state, preserving existing report/display and admin regrouping semantics.

REQ-PERF-001 endpoint bounds are `/api/health/freshness` p95<=1second and serialized JSON<=2097152bytes (2MiB), and admin `/api/admin/data-sources` p95<=1second and JSON<=3145728bytes (3MiB). Reports contain at most4096rows and128distinct bounded table labels; strings/reasons/identity fields are bounded and sanitized. The publisher and both actual route serializers enforce their byte caps. Oversize reports/responses produce explicit snapshot_payload_exceeded unknown/unavailable status and typed503, without a silently truncated or falsely complete report. The admin ownership extension is only the response-size guard, preserving its existing source aggregation.
