## Design

The design is in the three sections that follow: the value contract (one helper), the retained part 1 scope (exact fields and call sites), and part 2 (selection, the three implied-move states, failure propagation, the enumerated action changes and the library dependency).

## Value contract

A new module-level helper, `_finite_or_none(value)`, inserted in the Helpers block directly after `_safe_float` (L55 to L63 at d806bfd1), follows #1621's literal rules:

- a bool or non-scalar gives None;
- a value `float()` rejects (TypeError, ValueError, OverflowError) gives None;
- a non-finite result gives None;
- a finite real number is returned unchanged in value and type;
- a finite numeric string is returned as a float.

No threshold, clamp, rounding or zero is applied. It is the third copy of #1621's `_safe_num` contract (`scripts/fetch_earnings_calendar.py:95`, and the lib reader); consolidating them is a separate FEAT-CATALYST-001 question and is not done here.

## Part 2: valid-finite selection and the fail-closed implied move

### Selection (decision 2a of DECISION-INPUT.md, approved as "select valid finite data when available")

For `expected_move`: the coalesced value is the maximum over the per-row values that pass the value contract (`_finite_or_none`), or None. For `prev_close`: the first per-row value in query row order (`ORDER BY ec.ticker, ec.earnings_date`, no source priority, as today) that passes the contract, or None. A row's value that fails the contract is treated as if that row had supplied NULL for selection, so a valid finite sibling governs. Finite values keep value and type. Nothing is clamped, rounded or zeroed. Liquidity fields (options_volume, open_interest, market_cap, stock_volume, rv_1d_last_12q) keep `_max_non_null` unchanged: their invalid values are a separate, unapproved eligibility decision (DECISION-INPUT.md decision 4; DISCOVERED-ISSUES.md D1).

Two new event keys record what selection saw, so the embed can tell invalid from absent without re-reading rows: `expected_move_invalid` and `prev_close_invalid`, True only when at least one row supplied a present value (not None, NaN or pandas.NA) that fails the contract and no row supplied a valid value; False whenever a valid value exists (a valid sibling beside an invalid one gives False) and False when no row supplied the field. They are additive keys on the in-memory event dict; `persist_to_cloud_sql` does not write `brief['earnings']`, and the stdout JSON dump gains the two booleans.

### Three implied-move states at the guard input (decision 1a, approved as "prevent invalid-only data from producing a LONG CALL through the existing long-only guard")

Each of the two inputs has one of three field states, read from the coalesced value and its flag:

- `expected_move`: **valid** when `_finite_or_none` returns a number; **invalid** when it returns None and `expected_move_invalid` is True; **absent** otherwise (no row supplied it).
- `prev_close`: **valid** when `_finite_or_none` returns a number greater than 0 (the existing guard's `> 0` test, unchanged); **invalid** when it returns None and `prev_close_invalid` is True; **absent** otherwise, which includes a finite close that is not greater than 0 (Residual decision 3, unchanged from main).

The implied-move state follows from the pair, by the pure helper `_implied_move_state(em, close, em_invalid, close_invalid)`:

| | close valid | close invalid | close absent |
|---|---|---|---|
| **EM valid** | **valid** when `em / close * 100` is finite; **invalid** when it is not (overflow) | **invalid** | **absent** |
| **EM invalid** | **invalid** | **invalid** | **absent** |
| **EM absent** | **absent** | **absent** | **absent** |

Reading the matrix: the state is **absent** whenever either field is absent, because no implied move could have been formed from that pair whatever the other field held, so the documented None rule applies exactly as on main and this spec does not change it. The state is **invalid** only when an invalid value is the reason no finite implied move exists: the pair would have completed the quotient had the invalid value been valid, or both values are finite and the quotient itself is not. The state is **valid** only with two valid inputs and a finite quotient.

The call then sends exactly one shape per state:

- **valid:** `recommended_structure(..., implied_move_pct=<quotient>)`, as today for finite inputs.
- **absent:** `recommended_structure(..., implied_move_pct=None)`, as today; the keyword is not sent.
- **invalid:** `recommended_structure(..., implied_move_pct=None, implied_move_invalid=True)`. The library returns 'SKIP' exactly where it would otherwise consult the implied move (long-only mode, Q5, over-priced calibration confirmed) and is unchanged everywhere else, so IC mode and Q1 to Q4 rows never change.

No numeric surrogate is ever sent for a non-valid state. The precise rule: invalid-only input must not turn SKIP into LONG CALL. A valid finite sibling may legitimately change the action in either direction, which the owner accepted ("valid replacement data may legitimately change a recommendation").

**The two combinations the first review raised, and their outcomes.** (a) EM absent on every row and close invalid only: main gives LONG CALL (None rule; derived, not executed); after this spec, state absent, LONG CALL, unchanged. (b) EM invalid only and close absent on every row: main gives LONG CALL (None rule; derived); after this spec, state absent, LONG CALL, unchanged. The matrix keeps both unchanged because in each the absent field already prevents any implied move, so failing closed there would be a new missing-data policy, which the approval does not cover. If the owner wants (b) to fail closed instead, that is a one-cell change to the matrix (EM invalid, close absent: invalid) and is recorded here as the only open cell, not as a question requiring broad re-approval.

### Failure propagation at the call site (CLAUDE.md rule 3.7)

At d806bfd1, `_row_line` wraps the lib import, `score_quintile`, the implied read and the `recommended_structure` call in one `try:` (L2617) whose `except Exception:` (L2638 to L2645) logs nothing and renders the archetype fallback map. This spec does not extend that swallow and does not leave the new policy inside it:

- `_implied_move_state(...)` is called before the `try`. It is pure Python over two values and two booleans; a bug in it raises and propagates.
- The lib import and `score_quintile` stay inside the `try`. The `except Exception:` branch keeps rendering the fallback map (the brief still runs on a lib import failure, as on main) and gains one `logger.exception(...)` line naming the failure, matching the sibling block at L2404 to L2424. This is observability added to an existing fallback, not a new fallback.
- The `recommended_structure` call moves into the `try`'s `else:` block, so an exception raised by the call itself (a TypeError from a library without the keyword, the contradiction ValueError, or anything else) propagates out of `_build_earnings_embed` through `format_discord_messages_routed` (L3105, no handler) to `main()` (L3665, no handler), so the run ends with a traceback and no Discord post for any channel (overview, playbook, calendar, earnings); `persist_to_cloud_sql` (L3657) and the stdout JSON dump (L3654) have already completed by then and are kept. On main such an exception rendered 'CALL' silently; this is an enumerated behaviour change and the fail-loud reading of REQ-DATA-001 for an INTERNAL failure.

done_when 11 pins all three with a keyword-less stub, a raising stub, a kwargs-capturing stub and a failing import.
