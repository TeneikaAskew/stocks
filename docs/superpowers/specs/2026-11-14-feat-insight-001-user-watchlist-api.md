# A per-user watchlist in stocks Cloud SQL behind /api/me/watchlist

## Authority and status

Written 2026-11-14 from the owner's correction of 2026-11-13: "Solyra doesn't use Supabase, only
GCP. Stocks either." The approved per-user watchlist design
(`docs/superpowers/specs/2026-11-13-feat-insight-001-user-watchlist-v2.md` in TeneikaAskew/solyra:
Supabase tables and edge functions) and the approved ingest job's set read
(`docs/superpowers/specs/2026-11-13-feat-data-001-watched-ticker-ingest.md`: an HTTPS function with
a shared secret) both sat on Supabase. This spec puts the per-user list where every other per-user
record of the platform already lives: stocks Cloud SQL, behind the stocks API on Cloud Run, keyed
by the Firebase account id. Solyra's v3 spec consumes these routes; the ingest v2 spec reads the
owner-free set from the same tables. The owner records `status: approved` by merging this spec; no
code before that merge.

The two lock specs stand as approved and unchanged:
`docs/superpowers/specs/2026-11-13-feat-insight-001-watchlist-default-lock-a.md` (the default
list stays Discord's, every job reads only `'default'`, the read-only default endpoint) and
`docs/superpowers/specs/2026-11-13-feat-insight-001-watchlist-write-routes-410.md` (the two old
web write routes answer 410 once solyra calls the routes of this spec instead).

## Problem

Read in the code at origin/main b61b9124 and in production on 2026-11-13 (a read-only query of the
stocks `watchlists` table: every row owned by `'default'`; the default list is SPY, QQQ and IWM).

1. **The web watchlist is written to the jobs' table and never read back for the user.** Solyra's
   `useAddToWatchlist` and `useRemoveFromWatchlist` call `POST /api/insights/watchlist/add` and
   `DELETE /api/insights/watchlist/{ticker}`, which write the caller's email as `user_id` into
   `watchlists` (`platform/api/routers/insights.py:599-701`); the jobs read only `'default'` (stage
   A), so a signed-in user's picks go nowhere (stocks #1215, #1261).
2. **No remove control exists** in the web app although the route does (solyra #120).
3. **The approved replacement cannot be built.** The v2 design needed a Supabase project the owner
   has ruled out, and that the drafting session could not even read (v2, Decisions item 2).

What exists to reuse, read at origin/main b61b9124:

- `platform/api/auth.py:114-138` `_verify_bearer_email`: decodes the Firebase ID token with
  `firebase_admin.auth.verify_id_token` and returns the verified email; the decoded token also
  carries `uid` (the Firebase `sub`), which nothing returns today. `current_user_email` (`:148`)
  resolves the mode (open, firebase, iap).
- `gcp/database.py:93` `get_engine()` (SQLAlchemy over pg8000 and the Cloud SQL connector),
  `:244` `query_to_dataframe_strict` (raises on failure, Rule 3.7), `:984` `execute_sql`;
  `platform/api/routers/admin.py:1449-1450` shows a transaction (`with engine.begin() as conn`).
- `gcp/schema.sql` is idempotent and applied to production by the `apply-schema-on-change` Cloud
  Build trigger on every merge to main (`gcp/cloudbuild/apply-schema-cloudbuild.yaml`), so the two
  tables need no hand-run migration.
- `ticker_info` (`gcp/schema.sql:2404`: `name`, `exchange`, `asset_type`, `updated_at`) and
  `market_data_daily` (primary key `(ticker, date)`) hold the per-ticker facts a watchlist row shows;
  the FEAT-DATA-001 ingest job fills them for watched tickers.

## Non-goals

- No write to the shared `watchlists` table from these routes, ever. The default list stays
  Discord's and the CLI's (stage A), and the two old web write routes answer 410 (stage B) once
  solyra calls these routes.
- No job reads `user_watchlists` or `watched_tickers` except the FEAT-DATA-001 ingest job (its v2
  spec), which reads the owner-free set and no owner column. The brief, insight and signal
  surfaces keep reading only `'default'`.
- No stored per-ticker snapshot, no claim, no lease: `name`, `exchange`, `asset_type` and the latest
  daily bar are read from `ticker_info` and `market_data_daily` at request time, one index descent
  per row.
- No deletion of `watched_tickers` rows: a ticker nobody watches keeps its row and leaves the ingest
  set because it has no active membership.
- No UI (solyra v3), no change to the ranked route beyond stage A's, no Supabase of any kind.
- No per-user data visible to another user: every statement is scoped by `owner_uid`; there is no
  admin listing in this spec.

## Approaches considered

1. Chosen: two tables in stocks Cloud SQL (`watched_tickers`, `user_watchlists`) behind
   `/api/me/watchlist` routes in the stocks API; the Firebase uid from the verified token keys the
   membership and the verified email is stored beside it. Same cloud as everything else, the auth,
   the strict reader and the transaction pattern already exist, and the schema trigger applies the
   tables on merge.
2. Per-user rows in the existing `watchlists` table keyed by email behind the same routes (v2's
   rejected option 2). Rejected again: it keeps user rows in the jobs' table, which is the
   ambiguity the lock removes, and an email is not an immutable key (owner decision of 2026-11-13).
3. Supabase tables and edge functions (v2's choice). Ruled out by the owner on 2026-11-13; the
   project was never readable from the sessions that would have deployed it.

## Design

### Tables (gcp/schema.sql)

```sql
-- One row per ticker anyone has ever watched, shared by every watcher and read owner-free by
-- the FEAT-DATA-001 ingest job. Ten users on one ticker point at this one row; the ticker's bars,
-- indicators and ticker_info row are written once, by the jobs, never per user.
CREATE TABLE IF NOT EXISTS watched_tickers (
    ticker      VARCHAR(10)  PRIMARY KEY CHECK (ticker = UPPER(ticker) AND ticker ~ '^[A-Z0-9.]{1,10}$'),
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

-- One row per (user, ticker): membership only, no ticker data. owner_uid is the Firebase account
-- id (the token's uid), the immutable key REQ-TENANCY-001 asks for; owner_email is the verified
-- email, stored for display and audit and refreshed on every write. Removal is a soft delete so a
-- re-add keeps added_at.
CREATE TABLE IF NOT EXISTS user_watchlists (
    owner_uid    VARCHAR(128) NOT NULL,
    owner_email  VARCHAR(320) NOT NULL,
    ticker       VARCHAR(10)  NOT NULL REFERENCES watched_tickers(ticker),
    source       VARCHAR(20)  NULL,          -- 'ui', 'combobox-auto-add'
    added_at     TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    removed_at   TIMESTAMPTZ  NULL,
    PRIMARY KEY (owner_uid, ticker)
);
CREATE INDEX IF NOT EXISTS user_watchlists_active_idx        ON user_watchlists (owner_uid) WHERE removed_at IS NULL;
CREATE INDEX IF NOT EXISTS user_watchlists_ticker_active_idx ON user_watchlists (ticker)    WHERE removed_at IS NULL;
```

The number of active watchers of a ticker is counted from `user_watchlists` when needed, never
stored. The `apply-schema-on-change` build applies the file on merge; every statement is idempotent,
so a repeated apply changes nothing (`gcp/apply_schema.py`).

### Identity

`api.auth.current_user_identity(request) -> Optional[UserIdentity]`, `UserIdentity` a frozen
dataclass with `uid: str` and `email: str`. In firebase mode it decodes the bearer token the way
`_verify_bearer_email` does and returns the token's `uid` with the verified email; it returns `None`
without a bearer token, for a token firebase-admin rejects, for an unverified email, in open mode
(local development has no identity) and in iap mode (no uid; that path is retired in production).
`current_user_email` and `/api/me` (open, exact) are unchanged. The routes below are gated by the
auth middleware like every other `/api` route: nothing is added to `_OPEN_API_PREFIXES`.

### Routes (platform/api/routers/me_watchlist.py)

Models in `platform/api/schemas.py`, all `ApiModel`: `MeWatchlistAddRequest {ticker: str, source:
Literal['ui', 'combobox-auto-add']}`, `MeWatchlistRow {ticker: str, added_at: str, source:
Optional[str], name: Optional[str], exchange: Optional[str], asset_type: Optional[str],
last_daily_bar: Optional[str]}`, `MeWatchlistResponse {owner_email: str, as_of: str, tickers:
list[MeWatchlistRow]}`, `MeWatchlistRemoveResponse(MeWatchlistResponse) {removed: Literal[True]}`.
The router is included in `platform/api/main.py` beside the other routers.

- `GET /api/me/watchlist`. Without identity: 401, `detail = "sign in required"`, before any
  statement. Otherwise, through `query_to_dataframe_strict`:

  ```sql
  SELECT u.ticker, u.added_at, u.source, ti.name, ti.exchange, ti.asset_type,
         (SELECT MAX(m.date) FROM market_data_daily m
           WHERE m.ticker = u.ticker AND m.close IS NOT NULL) AS last_daily_bar
    FROM user_watchlists u
    LEFT JOIN ticker_info ti ON ti.ticker = u.ticker
   WHERE u.owner_uid = :owner_uid AND u.removed_at IS NULL
   ORDER BY u.added_at, u.ticker
  ```

  `added_at` and `as_of` (`datetime.now(timezone.utc)`) are ISO strings; `last_daily_bar` is an ISO
  date or null; `name`, `exchange` and `asset_type` are null when `ticker_info` has no row. A failed
  read answers 503 with `detail = f"watchlist read from Cloud SQL failed: {exc}"` (Rule 3.7: never
  an empty list for a failure). An empty result is 200 with `tickers: []`.
- `POST /api/me/watchlist`, body `MeWatchlistAddRequest`. The ticker is trimmed and upper-cased;
  422 unless it matches `^[A-Z0-9.]{1,10}$`. Then one transaction (`with get_engine().begin() as
  conn`) that serializes admission per owner before it counts, because two concurrent adds at 199
  rows would otherwise both see 199 and both commit:

  ```sql
  SELECT pg_advisory_xact_lock(hashtext(:owner_uid));
  SELECT COUNT(*) FROM user_watchlists WHERE owner_uid = :owner_uid AND removed_at IS NULL;  -- 200: rollback, 409 "watchlist full"
  INSERT INTO watched_tickers (ticker) VALUES (:ticker) ON CONFLICT (ticker) DO NOTHING;
  INSERT INTO user_watchlists (owner_uid, owner_email, ticker, source)
       VALUES (:owner_uid, :owner_email, :ticker, :source)
  ON CONFLICT (owner_uid, ticker) DO UPDATE
          SET removed_at = NULL, source = EXCLUDED.source, owner_email = EXCLUDED.owner_email;
  ```

  `added_at` is never written on conflict, so a duplicate add or a remove-then-re-add keeps the
  original. The handler then answers the GET body (200).
- `DELETE /api/me/watchlist/{ticker}`: `UPDATE user_watchlists SET removed_at = NOW() WHERE
  owner_uid = :owner_uid AND ticker = :ticker AND removed_at IS NULL`; 404 when no row matched;
  otherwise the GET body plus `removed: true`. The `watched_tickers` row is never deleted.

Every statement carries `owner_uid` from the verified token, never from the body or a query
parameter. The router never names the `watchlists` table.

### Capacity (CLAUDE.md Rule 0)

No scheduled workload. Per request: GET is one query over at most 200 rows, each with one index
descent on `market_data_daily (ticker, date)` for `MAX(date)` and one on `ticker_info`; POST is one
count, one transaction of two statements, then the GET query; DELETE is one update then the GET
query. Volume: at most 200 active rows per user; `watched_tickers` grows by one row per distinct
ticker ever watched. Wall-clock: milliseconds per statement over pg8000. Cost: none beyond the
always-on instance.

## Risks

- A user adds a ticker stocks has never fetched: `last_daily_bar` is null until the ingest job's
  next run; solyra v3 shows "data arrives after tonight's fetch" and then "no data for this symbol".
- The schema build and the API deploy run on the same merge; a request landing before the apply
  completes answers 503 (undefined table), an explicit failure, not a fabricated empty list.
- Open mode locally answers 401 on these routes; the solyra dev server against staging signs in
  through Firebase and sees the real list.
- A user's email changes: the uid is the key and the email is refreshed on the next write.
- The 200-row cap per user is separate from the ingest job's 50-ticker ceiling (ingest v2); the
  job records an overflow note when the active set exceeds it.

## Decisions (owner, 2026-11-13)

1. GCP only; no Supabase in solyra or stocks.
2. Owner key: the Firebase account id, with the verified email stored beside it (unchanged).
3. Dedup: one shared `watched_tickers` row per ticker; membership rows point at it (unchanged).
4. Per-user rows never reach the brief, insight or signal jobs (unchanged); the ingest job reads
   the owner-free set from these tables (ingest v2).
5. The two old web write routes: blocked with 410 once solyra calls these routes (stage B, unchanged).
