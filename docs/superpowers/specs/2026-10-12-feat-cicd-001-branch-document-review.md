# Bind implementation documentation to committed source

## Decision requested

Approve this explicit documentation review policy before implementation. This scratch draft is not approved, does not change existing delivery rules today and does not authorize any AV implementation. Broad watcher coverage remains unchanged. Existing documentation review requires no new findings before merge but cannot use a feature SHA as a trunk baseline; squash also removes feature ancestry. A committed, exact source/body identity record resolves identity without claiming to authenticate an external CODE review.

## Local identity and external review are separate

The new record is a locally reproducible identity declaration. Its producer is `scripts/maintenance/doc_source_snapshot.py`; its verifier is in the same protected module, called by `scripts/maintenance/docs_audit.py`. Anyone may reproduce a record: it contains no signature, reviewer assertion, approval Boolean, issue-comment authority or fabricated authentication. Audit output says `implementation-source identity matched; external CODE review under existing rules; rollout pending`. It does not say `verified review`, and does not update the existing verified/trunk/deployment marker.

Authenticated external CODE review remains the repository's existing CODE-review prerequisite: current-head external review by the required reviewers, green required checks and resolved conversations, enforced through the normal merge process. The local CLI has no external-review trust anchor and cannot establish those facts. No new attestation service, API fetch, credential or network request is introduced. An identity-matched audit alone never permits merge; CODE reviewers must read the corresponding source and notes. Misstating review approval or deployed status is a review failure independently of identity matching.

## Exact record and committed-source contract

Only `docs/review-evidence/site-source-snapshot.json` is eligible. It lies outside watched runtime roots and outside `docs/product/`; records elsewhere do not affect findings. The producer reads committed trees, never uncommitted worktree content, and writes this sidecar after successful complete verification. CLI:

`python3 scripts/maintenance/doc_source_snapshot.py produce --policy-ref origin/main --source-ref HEAD --output docs/review-evidence/site-source-snapshot.json`

`python3 scripts/maintenance/doc_source_snapshot.py verify --policy-ref origin/main --source-ref HEAD --record docs/review-evidence/site-source-snapshot.json --max-seconds 5 --max-input-bytes 8388608 --max-entries 20000`

The verifier consumes the record from the committed `--source-ref` tree. Production callers cannot raise these fixed limits. Tests may lower them to exercise refusal. Both refs resolve to actual commits before enumeration; CLI arguments are literal argv, never shell fragments. No partial record is installed on failure. An existing output file is replaced atomically only after complete successful production.

Version1 has exactly these JSON keys: `version` (integer1), `context` (literal `implementation-source; rollout-pending`), `object_format` (`sha1` or `sha256`), `policy` (below), `baseline` (below), `source_entries`, `source_identity_sha256`, `document_path` (literal `docs/product/03-SITE-TRACEABILITY.md`), `document_body_sha256`. Unknown/duplicate keys, invalid UTF-8, floats, extra JSON values and unsupported versions are refused. Canonical bytes are UTF-8 JSON with keys sorted, no insignificant whitespace, ordinary JSON string escapes, no NaN, and one final LF. Hashes use SHA256 lowercase64hex. Arrays are ordered by UTF-8 path bytes. Entries have exactly `path`, `mode`, `blob_oid`, `size_bytes`; OID width follows object_format, modes only100644/100755. Paths must be normalized repository-relative UTF-8, with no empty/dot/dot-dot components, leading slash, backslash, control bytes or duplicate entries. Symlinks/gitlinks and unreadable/missing objects in admitted scopes make proof unavailable; they are not skipped.

`policy` contains exactly `registry_path`, `registry_blob_oid`, `document_path`, `watch_paths`, `policy_identity_sha256`. The registry path is the actual registry path already used by docs_audit, not an authored replacement. The trusted policy ref supplies that registry's complete unchanged SITE watch paths. `watch_paths` and their source enumeration are derived by the existing exact-path/descendant-prefix semantics, including every new descendant; no exclusions or authored subsets are accepted. Policy identity is SHA256 of canonical policy fields excluding its own hash. The verifier compares all fields to policy derived independently from the trusted ref. Changes to policy invalidate old records. The new protocol cannot narrow existing broad paths.

`baseline` contains exactly `source_entries`, `source_identity_sha256`, `document_body_sha256`, derived from the actual trusted policy tree at production time. Its manifest uses the same entry schema and limits. These baseline facts are informational context after squash, not authority and not a substitute for the existing trunk marker. The branch acceptance route compares them to the independently enumerated current policy-ref tree and body. The landed acceptance route is available only if the record's complete source manifest and body also equal the independently enumerated current policy-ref tree and body; its older baseline is then explicitly labeled historical context. There is no caller-selected after-merge bypass. No unavailable baseline/feature commit is accepted as proof. There is deliberately no required feature SHA: authoritative source revision identity is `source_identity_sha256`, independently recoverable from the actual current commit's scoped entries. SHA256 is over canonical `{object_format,policy_identity_sha256,source_entries}`; the record's own path is outside these scopes. Git committed blob OIDs, modes and paths define content identity; inspect object existence/type/size through bounded Git plumbing and compare independently enumerated current entries. Do not buffer all186MiB of file contents or replace missing objects with declared hashes.

Reject replacement refs, grafts or other history/object rewriting that makes committed identity ambiguous; run Git with replacements disabled as an additional guard, not a substitute for refusal. Unsupported/shallow state that prevents resolving the policy/trunk marker or required objects is explicit unavailable state. Fresh-clone tests fetch enough main history for its existing trunk marker; they do not fetch the original feature SHA.

Document identity is SHA256 over strict-UTF-8 committed SITE text processed by the existing `_without_marker` normalization, then encoded UTF-8 without additional normalization. That existing normalization removes only marker-owned fields/anchor blank lines and preserves extra marker prose. The sidecar supplies all new protocol metadata; SITE receives no self-referential snapshot hash. All backend notes and every frontend/progress/evidence byte participate in body identity. Existing marker fields remain protected from feature edits. No record or verified status is accepted for a dirty SITE worktree during the audit.

## Exact document allowance

Approved capability specs may add the optional frontmatter field:

`site_source_notes: [JOURNAL-09, CHARTS-02]`

IDs are existing unique SITE Chain element IDs, sorted and duplicate-free. The gate reads this field only from the capability's immutable approved spec at its trusted merge base. Unknown IDs, duplicate fields or malformed declarations are refused; a feature cannot approve its own selector. Initial protocol implementation has no such declaration and edits no SITE bytes.

The only permitted new area is an appended `## Implementation-source notes` section with exactly the table header `| FEAT | Component | Backend source and tests (implementation only; rollout pending) |`. A feature may add/update only its own rows `(FEAT-ID, declared Component-ID)` there; each pair is unique and ordered. Empty/duplicate headings, structural/header changes, removed foreign rows and undeclared IDs are refused. Removing its existing note requires a declared ID as well. Outside its allowed table cells, byte-for-byte SITE content is preserved; every existing Chain/checklist row and every frontend/progress/S/T/V/Te/deployment claim is untouched. Notes contain implementation-only prose and local repository backend/source/test references, not frontend screenshots, remote frontend implementation links or assertions of deployed availability. External CODE review enforces prose meaning; the gate enforces exact structural ownership and byte boundaries, not semantic authentication. Existing mixed backend/frontend Chain cells are therefore never opened by this allowance.

## Audit routing and bootstrap

For SITE only, a completely valid matching identity record replaces the two drift questions `check_changed_since` and `check_doc_changed_since` with explicit identity-matched context. Missing/invalid/mismatched records run the original checks and add a provenance finding. Ordinary marker shape/date/unknown/ancestry checks, bad references, incorrect descriptions, missing tests and every other audit check still run. Existing `Against` remains a genuine trunk baseline; this feature never stamps an unavailable feature SHA, moves Last reviewed, marks deployed verification or suppresses marker findings. Other documents retain original behavior. `--stamp --verify` remains trunk-only and gains no branch-stamping exception.

Stage1: owner approval, then root publishes the DOC-only approved spec and precise skill/template policy wording on main before implementation. These docs explicitly adopt the local-identity/external-review distinction; they do not alter scripts or watchers. Existing approved specs remain immutable. Current rules continue until that approved policy lands.

Stage2: one CICD implementation PR changes the protected producer/verifier, auditor, gate ownership checks and suites, plus its permitted catalog/traceability/plan and the sidecar. It edits no SITE content, registry watcher or pinned workflow. Thus the unchanged BASE product-scope gate has no new SITE edit to reject. The actual proposed HEAD auditor may evaluate the identity record for the unchanged SITE body against the new committed source; branch-versus-main no-new comparison is performed with actual CLIs, not a fabricated trusted BASE verdict. This is the existing branch-audit execution model, explicitly limited to this approved protocol introduction. All actual BASE gate checks, unchanged BASE suite, four-seat review and complete affected suites must pass; no exception to no-new findings or required checks is authorized. If actual evidence cannot satisfy this sequence, stop and return to owner with a separate concrete policy decision; do not self-waive it.

Stage3: only after Stage2 is on main may other capability implementation branches use the now-trusted approved-spec SITE-note allowance. Their records bind exact source and entire body; later unrelated watched-code or body edits invalidate the record and require reproduction and current-head CODE review. After each squash, a fresh main clone verifies identity independently of feature ancestry. Separate DOC main/staging close-out truthfully updates the historical trunk marker and deployed evidence only after actual checks; a matching source record never completes that close-out.

## Bounds and acceptance controls

One monotonic deadline starts before record/ref/policy/object setup and ends after parsing, enumeration, object metadata checks, canonical identity/body calculation and final verdict/output. All Git child processes share the remaining budget; deadline refusal terminates/reaps them. No background or partial-success path survives a timeout. There is no authentication/network I/O. Admission ceilings are combined across current and baseline manifests: at most20000 entry records; at most8388608 input bytes across record, Git listings and object metadata (each actual byte read counts, including repeated reads); committed SITE body also counts. Stream bounded reads and reject before exceeding either ceiling. Eight-MiB ceiling is a deliberate fail-closed capacity limit, not an assertion that every 20000-entry input fits. Output records must also fit the same ceiling before installation.

Actual CLI verdict JSON reports success/unverified, entry count, actual counted bytes, source/policy/body identities, elapsed seconds and refusal reason. Cold/ordinary actual runs must complete within5seconds on the normal runner; unsupported or slower input stays unverified. Existing tree approximately1519entries/186MiB of blobs is context, not measured performance evidence. New Cloud Run/jobs/schedulers/vendor/API/auth calls: zero; existing public hosted-runner allocation incremental billed cost zero. Full-render60seconds/512MiB and registry285second limits remain independent.

Tests must use actual producer and consumer CLIs, actual branches, squash and fresh clone. Accepted control is a real record produced for real committed source/body. Refused controls mutate committed source mode/blob/path/add/delete or notes/body/policy after production; corrupt/drop producer output; provide well-formed wrong identities; exceed record/listing/body/entry/deadline limits; introduce unsupported path/type/replacement state; or change another feature's/undeclared/frontend bytes. Every refused control checks nonzero/unverified or actual retained findings, with no successful placeholder return. Producer nonzero or partial output must leave no new installed record. Exact matching records do not authenticate external reviewers or certify deployment: tests verify those labels and preserve an unrelated audit finding.
