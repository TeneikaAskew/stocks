# Rate and ETF-yield input publications

The user authorized this proposed addition with “Keep going” after its explicit approval question. This local approved proposal is not canonical DOC/main delivery or deployment evidence. Existing approved source/DATA specifications remain unchanged.

## Problem and ownership

Source A7 requires actual acknowledged input evidence but expressly does not own a FRED/DATA writer. Current daily_rates is mutable and its S&P500 yield constant is not measured ETF yield. Approved DATA includes ETF_PROFILE receipts but limits its explicit reference ACK producer clause to DIVIDENDS/SPLITS. Complete input readiness therefore needs this separately DATA-owned addition. The native options source foundation continues independently.

## Scope and approaches

Implement the immutable provider and actual acknowledgement path. Mutable-cache timestamps alone cannot meet the historical contract. Reusing an options journal would cross ownership. Use DATA-owned rate storage and the already specified DATA ETF receipt/ACK protocol instead. Preserve the existing daily_rates cache and its configured S&P yield column; that column remains an explicitly unqualified assumption, not an observed ETF input. No financial formula, schedule, resource, source entitlement or automatic application retry is added.

Existing broad FRED backfill is outside this finite cutover. Reject --backfill and explicit windows of more than32 inclusive calendar dates before vendor, archive, maintenance or financial I/O; do not split requests or truncate responses. The default remains the existing14-day lookback. Accept bounded valid --start/--end, reject reversed/invalid dates. Count every returned dated observation, including missing values, toward32. Preserve existing CLI operation; add --dry-run as a read-only validated plan, not a default that disables the scheduled job.

## Rate storage and transaction boundary

Use three provider-specific SQL tables, rather than the initial proposal's ambiguous mixed header/body pair: fred_rate_revisions (durable capture intent and financial header), fred_rate_payloads (exact original response BYTEA plus canonical normalized observations), fred_rate_publications (immutable financial ACK). No new GCS namespace or lifecycle writer is required. The immutable SQL artifact identity identifies the exact payload row and capture UUID; do not manufacture a GCS generation or claim object-storage proof. Raw and normalized hashes remain distinct.

The revision header has a generated capture UUID, positive noncycling capture sequence, unique stable retry key, exact DGS3MO request-window/configuration/code identity, state, admitted-at, nullable immutable intent-known-at, and once-bound actual response-completion/source identity, source/normalized hashes/byte counts and payload expiry. Operational reservations, failed/orphan states and narrowly checked body-removal receipt/ACK fields are distinguished from financial fields. Pending intent is not a financial revision. Bind financial identity once in the source transaction; after that all financial/header facts are immutable. Publish only validated full-response records, preserving missing observations. Runtime cannot forge intent clocks, financial bindings, publication or expiry evidence through direct DML. Owner-defined, pinned-search-path entrypoints implement exact transitions; no arbitrary SQL/callback/plugin interface or public administrative bypass.

The payload has a capture-ID PK/FK, immutable original entity bytes, canonical normalized rows, exact hashes/sizes and expiry. Store the original uncompressed HTTP entity bytes before JSON reserialization; hash precisely those retained bytes. No credentials occur in stored request identity. Metadata/publication can survive body deletion. Publication has revision-ID PK/FK, actual available_at and fixed acknowledgement-source kind; tuples cannot be updated/deleted by runtime. daily_rates remains a mutable cache and is expressly outside the immutable-tuple prohibition.

One real connection owns the financial transaction. A connection-taking batch helper in gcp/fred_rate_publication.py inserts the payload, binds the financial revision, and conditionally upserts the existing daily_rates cache in the same transaction. It must not wrap existing upsert_dataframe, which owns independent transactions. Cache updates follow actual source-capture precedence; an older response acknowledging late cannot overwrite newer data. Equal capture clocks with different content are unavailable, not UUID-ordered winners.

The four bounded phases are: (1) atomic admission/pre-source recovery lookup plus eligible cleanup; (2) intent acknowledgement at the real later server clock, and eligible prior-removal ACK; (3) full source/header/payload/cache transaction; (4) financial post-COMMIT ACK and reservation finalization. The authoritative terminal is a structured log emitted only after the actual phase4 response and bounded cleanup, with no additional database exchange or job_runs write. Earlier refusal/error paths also emit their actual structured terminal after bounded cleanup; no unpriced terminal SQL is added. Use a dedicated low-level pg8000 DBAPI connection with its public autocommit=True, obtained through the public Cloud SQL Connector connect API (or explicit loopback pg8000 connection in local tests). DATA owns this bounded connection factory inside gcp/fred_rate_publication.py; retain the same configured instance/database/user/credential selection and lazy connector refresh, with explicit remaining-time limits and closure. Do not extract private SQLAlchemy pool hooks or change the shared engine. Each phase uses the supported public cursor.execute(operation) simple-query path with no parameter arguments or stream, as one fixed function statement in a single atomic implicit server transaction. Parameterized pg8000 execute_unnamed is excluded because its Parse/Describe/Bind exchanges would exceed the eight-interaction budget. Only the fixed qualified owner function name and SQL template may form SQL syntax. Canonical UTF8 JSON descriptor bytes, including bounded original entity bytes encoded as base64 when required, are converted using bytes.hex() to lowercase hex, strictly validated as [0-9a-f] and decoded server-side into the fixed typed envelope. No raw external text, identifier, function name or SQL fragment is interpolated. Cap the full JSON envelope before encoding at2MiB, the hex SQL operation at4MiB plus256 fixed template bytes, and new transient transport buffers at16MiB; reject overflow before building or sending the operation. The retained raw1MiB/normalized64KiB/metadata64KiB caps remain independent. Tests include adversarial quotes, backslashes, Unicode and binary entity bytes, exact hash/round-trip validation, oversized envelopes and credentials absent from SQL/error logs. Never log the operation or body. Actual simple-protocol flush/receive evidence, not merely one Python execute call, is required. Its successfully completed idle ReadyForQuery response is the actual transaction acknowledgement; only a later independent phase records its ACK clock. No explicit no-op COMMIT or implicit client BEGIN is issued. At most8 total actual database interactions are allowed: four phase statements and at most four startup/authentication/protocol/initialization interactions. Count cold startup and recovery as well as queries; connector authentication work is independently timed and charged. No hidden pre-ping, dialect/reflection, per-observation or metadata query is allowed. An early actual-pg8000 cold-driver proof must establish this composition within8 before the ready plan can progress to full writer cutover; source inspection or a mocked execute counter is insufficient. A failed/denied branch may finish earlier. If actual driver composition cannot meet this bound, activation is refused; do not silently omit acknowledgement or increase the bound.

The intent transaction commits first; phase2 captures only the actual later server clock, and vendor work starts only after that phase commits successfully. A lost intent ACK is uncertain and fails closed. Server-derived transaction provenance must reject intent, financial or removal ACK in the same outer transaction, including open/released/nested savepoints; tuple xmin inequality alone is not commit evidence. Capture source/cache commits before financial publication; phase4 uses the actual later server clock. Never substitute source date, fetched_at, transaction start or cache update for either ACK. Tests kill the actual producer after each commit and before its ACK. Unknown commit outcomes require bounded exact-identity reconciliation; no presumed success or new vendor call.

The unique first lookup identity is the fixed job plus native execution/task identity, excluding retry attempt number, request window and code/configuration. Perform that lookup before evaluating moving date defaults. Freeze the initially resolved bounded window, code/configuration and explicit CLI arguments in its durable intent. A retry reuses the stored window across UTC/local midnight; explicitly supplied mismatches or changed code/configuration refuse rather than generate a new key. Only a genuinely new execution identity may resolve fresh defaults and create an intent.
