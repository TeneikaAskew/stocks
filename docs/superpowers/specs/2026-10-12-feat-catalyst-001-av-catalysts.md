# Reconcile AV earnings revisions and make catalyst ingestion reproducible

## Authorization and intake

This records the six-stage AV/GCP remediation plan authorized on 2026-10-12: "Proceed with the plan, executing inn parallel". Parallel work uses one isolated implementation branch and author per capability. FEAT-CATALYST-001 owns earnings/catalyst data contracts. These refinements address the independent review of spec PR #1392 within that authorized scope; they do not claim unrelated product issues closed or delegate operational responsibility on the user's behalf.

## Problem

AAPL June-quarter actual EPS is NULL in Cloud SQL but 2.02 in AV, and older quarter values changed. Existing history is skipped outside its reporting window. News scores differ from current AV; swallowed source or eligibility failures can appear empty/successful, nullable conflict keys permit duplicates, and exception logs can expose the API key. Refreshing mutable earnings or estimates without permanent vintages introduces future corrections into historical reads. The current point-in-time API still reads the latest cache. Reaction price math can mistake a split for earnings performance.

## Non-goals

No expansion to all AV APIs, strategy/model promotion, fabricated values, inferred legacy publication clocks, unbounded historical backfill or claim that current derived reaction/views or revised adjusted price history are safe for replay. This capability does not edit deployment, scheduler, IAM or bucket lifecycle files; their required changes are an explicit FEAT-DEPLOY-001 promotion dependency.

## Approaches considered

1. Repair existing contracts, preserve permanent SQL observations, archive original responses and deploy bounded source-backed changes: selected.
2. Replace the ingestion platform: unnecessary scope and operational risk.
3. Change schedules alone: leaves corruption, provenance loss and misleading outcomes unresolved.

## Design

### Strict source and universe outcomes

Use strict source transport/payload validation and `gcp.database.query_to_dataframe_strict` for all eligibility, existing-history, reporting-window and incremental-cursor reads used by these jobs. A successful zero-row query is a valid empty result; connection, authentication, schema and query failures propagate as source/eligibility errors. They cannot be converted to a smaller fallback/watchlist universe with a successful outcome. An explicitly selected CLI universe can bypass unused eligibility queries; any required query failure marks the run failed or partial and nonzero. If an independent valid group is processed, persist it durably before reporting the incomplete run.

Validated empty AV arrays differ from HTTP/transport failure, vendor Information/Note/Error responses, invalid shapes and rejected required fields. Persist bounded groups durably before advancing. Earnings/insider groups remain per ticker; news uses the bounded response/row/byte batching contract below, never an unbounded complete-universe frame. Existing `job_runs` receives success, validated empty, partial or failed status, expected/attempted/processed/failed counts, rows committed, saturation, and source-specific failure classifications. A news response reaching its 1,000-article limit is incomplete unless a bounded window strategy proves full coverage. Deliberate scope exclusions are counted separately from malformed records. Failures never lose already committed groups, and unavailable financial values remain NULL.

### Bounded earnings refresh and separated backfill phases

Refresh daily recently reported incomplete quarters using a configured, documented lookback. Weekly reconciliation selects the oldest fetched-at clocks for at most 100 existing tickers in one batched strict eligibility query. Preserve explicit `--force`, while keeping a separately documented safety cap. Do not falsely mark cap-truncated work complete.

The existing `gcp/fetchers/fetch_earnings_history.py` may chain `gcp/fetchers/fetch_market_data.py::_run_backfill` under `BACKFILL_ALL_HISTORY=true`. The approximately 330-second primary estimate excludes that chain and Yahoo transport. Every targeted repair command includes `--no-backfill`; it cannot silently launch the broad market universe. Scheduled existing behavior retains its deployed 28,800-second timeout and its explicit chain unless the DEPLOY spec changes it with complete-path evidence. Record primary and backfill phases separately, including their failure totals. A backfill exception or reported failed groups yields partial/nonzero overall status even when earnings commits succeeded. Preserve the primary commits. Before another group starts, enforce the remaining execution budget; exhausted budgets record unprocessed groups and exit incomplete rather than timing out without a terminal record.

### Original-response archives

Archive original response bytes for NEWS_SENTIMENT, EARNINGS, EARNINGS_ESTIMATES and the complete EARNINGS_CALENDAR CSV before parsing/filtering removes vendor fields. Immutable gzip envelopes retain reconstructable original bytes, their SHA256, safe query parameters/query hash, UTC retrieval time, endpoint, code/pipeline version and object URI. Credential values and credential-bearing URLs are excluded from metadata and logs; exceptions log a controlled class/code, not request text. Object creation uses a unique observation identity and a no-overwrite precondition; retrying the same captured observation is idempotent.

A configured archive bucket is mandatory outside dry-run. Missing configuration or failed upload cannot produce provenance-complete SQL rows. Dry-run writes neither GCS nor SQL. The producer prefix is exactly `av/raw/`. Raw retention is 90 days only after DEPLOY lifecycle convergence; permanent SQL earnings and estimates observations are not deleted when raw objects expire. Do not apply an unrelated bucket-wide deletion policy.

### Earnings revisions and independent Yahoo timing evidence

Keep `earnings_history` as the latest live cache and add permanent append-only `earnings_history_revisions`, indexed by ticker/fiscal_date_ending/known_at descending/revision_id descending. Versions retain all normalized EPS, surprise, reported-date and timing fields, canonical value/hash, AV retrieval clock and response provenance. Install the source lock, journal table, trigger, guard and real-clock legacy seed atomically. An AFTER INSERT/UPDATE trigger preserves the preceding cache value when necessary and appends changed/new values in the same transaction as the cache write. AFTER avoids speculative BEFORE INSERT side effects from ON CONFLICT. Legacy rows are observed at migration time with `availability_quality=observed_legacy` and unknown source clock; never backdate from report/fiscal dates or inserted_at. Same-clock versions order by revision_id. Full value comparison suppresses unchanged financial versions; A-to-B-to-A reversions remain distinct. Cache freshness updates do not rewrite permanent values. Rollback affects cache and journal together, and alternate cache writers remain journaled with honest source quality.

Yahoo timing is an independent observation. Capture the actual yfinance earnings-date DataFrame returned by the library, including timezone-aware index values and available fields, request symbol/limit, retrieval clock, library/version and content hash. Store append-only `earnings_timing_observations` and link each applicable quarter revision through `yahoo_timing_observation_id`. This is a versioned library observation, not a claim that original Yahoo wire bytes were captured. Its timestamp and attribution are separate from AV response provenance. Unknown legacy Yahoo availability remains unknown. A timing-only correction creates a new quarter revision with its actual Yahoo observation; an absent/failed Yahoo response cannot be attributed to AV or represented as a fresh Yahoo confirmation. Optional-source failure/degradation is explicit in run accounting, and an explicit no-Yahoo mode is documented as such.

### Immutable estimate vintages and aware readers

`gcp/fetchers/fetch_av_earnings_estimates.py` validates the actual `{symbol, estimates:[...]}` contract and retains every estimate field, including EPS/revenue ranges, analyst counts and revision history. Store immutable `av_earnings_estimates_observations` with an observation identity, ticker, fiscal_date_ending, horizon, known_at, source retrieval clock, raw URI/hash and complete JSONB payload. A fiscal year and fiscal quarter may have the same date; horizon participates in identity. Include observation/known_at in the vintage key. An idempotent retry of one captured response does not append duplicate observations; a later retrieval never overwrites an earlier vintage. SQL vintages remain queryable after raw expiry.

`lib/earnings_history.py` provides aware-cutoff earnings and estimate readers. Historical reads select the latest revision/observation with known_at <= as_of per logical quarter/horizon in one bounded query, expose explicit pre-observation coverage gaps and never substitute the live cache or current vendor response. Date-only API requests resolve to the end of that exchange date in America/New_York, using an aware cutoff and the shared calendar/time helper; database session timezone is irrelevant. `platform/api/routers/catalysts.py` routes `/api/catalysts/asof/{ticker}` earnings history through this reader, replacing the direct live-cache query. Legacy gaps are surfaced as section availability/provenance, not hidden by the endpoint's generic empty-on-exception wrapper. No corrected EPS/surprise/report date observed after the cutoff may appear. The earnings-reaction source adapter passes an aware as_of when supplied. For every explicitly requested historical/as_of snapshot, omit current unversioned `news_sentiment`, `sec_filings`, `insider_transactions`, `earnings_calendar` and `market_data_daily` values unless an observation-time version satisfying the cutoff is actually available. Return their existing data fields empty/null with an explicit section-level `status=unavailable`, `reason=historical_provenance_unavailable` and cutoff; never return current values alongside only a warning. A late backfill/correction dated before the cutoff must not enter any section. This chooses suppression, rather than expanding the feature to version all five sources.

All sections that are actually queried, including live/default requests, use strict database reads. Replace the generic `_safe` empty-on-exception behavior for the entire snapshot endpoint: database/authentication/schema failures produce explicit section `status=error/unavailable`, controlled error class and reason, or a failed request. They are distinguishable from a successful zero-row section (`status=empty`) and from a historical section that was intentionally not queried. Preserve section counts only as qualified by these statuses. Neither the revision-reader error nor any other section failure may become an unmarked `[]`. Current derived tables remain explicitly live-only.

### Corporate-action-safe reaction inputs

For live continuous reaction return/price metrics, use the shared FEAT-DATA-001 price-basis helper to scale all OHLC consistently by adjusted_close/close; retain raw bars separately for as-traded levels, execution/strikes and audit. Never substitute adjusted Close alone. Reject missing, nonfinite or nonpositive factors. Known split windows without a complete, validated common-basis input set are unavailable and produce no reaction alpha: an exact -50 percent two-for-one split and smaller split must be rejected, independent of the old greater-than-50-percent anomaly guard.

Historical/as_of reaction evaluation may use only a price-factor/corporate-action vintage known by that cutoff. Current revised adjusted history is insufficient. If such vintage evidence is absent, or a split-window safety check cannot establish compatible prices, reject the input with explicit unavailable status rather than recomputing historical features from today's corrections. Unversioned reactions/views remain live-only. The dependent shared helper contract is in `docs/superpowers/specs/2026-10-12-feat-data-001-av-market-data.md`; no broad market-data backfill is implicitly authorized by reaction evaluation.

### Provenance of every new reaction row

Live-only status does not waive REQ-DATA-003. Each newly produced `earnings_reactions` row carries its source earnings revision ID and known_at, applicable independent Yahoo timing observation ID, the actual source/as_of clock, price-factor/basis and source-quality versions, pipeline ID/version, complete resolved configuration plus hash, rule/model identifier/version, durable input artifact ID/hash and code commit/image identity. Retain the exact selected earnings/timing/price/factor inputs in a permanent SQL `earnings_reaction_input_artifacts` manifest, keyed by its content hash; the row links that artifact. An optional GCS copy does not make a 90-day object the sole lasting provenance. Record actual observation clocks for live cached-price inputs, without inventing historical vendor availability. Same inputs/configuration/code produce the same artifact identity; changing a source revision, factor, timing, rule or configuration changes the identity and propagates into the derived row. SQL writes commit artifact/derived linkage consistently and cannot claim a complete new row with missing required provenance.

Historical/as_of reaction generation remains refused when source/factor vintages are unavailable. Existing derived rows with unreconstructable provenance remain tagged `legacy_provenance_unavailable`; do not manufacture old source/configuration versions. New live results expose their provenance explicitly, and current overwritten reaction rows are not advertised as an historical revision store. The API/reader distinguishes legacy unverified provenance from validated new output.

### NULL-safe source identity

Use a stable non-null `source_identity_hash` for every persisted news/insider row, derived from a documented canonical typed source identity. Preserve NULL as NULL inside canonical serialization, rather than defaulting executive/type/shares/price to invented values. News identity uses ticker and publication instant plus vendor article identity/URL when available; missing-URL identity uses the documented source/title/publication tuple and carries content-derived quality. Insider identity uses the existing economic key fields, including transaction date and nullable executive/type/shares/price; canonical numeric normalization makes equivalent representations equal. Sentiment/relevance and mutable descriptive enrichment do not alter article identity. Unique non-null identities drive ON CONFLICT, so replay of identical nullable payloads converges and cannot inflate insider-cluster counts.

All news writers use the same canonical identity preparation and identity conflict target: `gcp/fetchers/fetch_news_sentiment.py`, the news block of `gcp/backfill_ticker.py`, `gcp/fetchers/fetch_rss_news.py::write_to_cloud_sql`, and `scripts/backfill_news_sentiment.py`. Repository-wide writer discovery is an acceptance check; no identified writer may keep the old nullable conflict path after identity enforcement. Maintain the existing `(ticker,published_ts,url)` constraint during the compatibility transition so still-running old images do not fail with an invalid ON CONFLICT target. Deploy schema preparation and updated compatible writers before enforcing the final non-null identity path; drain/replace old writer images before final enforcement. Do not claim that a trigger supplying a hash alone makes old NULL-key ON CONFLICT statements idempotent. The migration/readiness test replays every actual writer under transitional and final schemas, covering missing and nonmissing URLs. The insider writer uses the same documented non-null economic identity contract.

Migration backfills legacy identities in bounded groups and audits existing duplicates/collisions before enforcing uniqueness. Preserve original financial evidence; do not blindly delete legacy rows to satisfy an index. Any actual duplicate repair must be documented, source-backed and validated before promoting affected consumers. Hash collision or ambiguous source-identity quality is an explicit data-quality result, not a fabricated source ID.
