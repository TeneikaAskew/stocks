# Replays on Discord and the API read bars from the table or say they cannot

## Problem

The owner's rule, 2026-11-13: every replay reads 1-minute bars only from the store the nightly pull fills, the Cloud SQL table `market_data_intraday` (interval `1min`). No replay fetches bars from AlphaVantage or anywhere else. When the table does not have the ticker or the day, the replay says so. Read at `main` 8712afb6:

That job pulls 1-min bars from AlphaVantage and writes them to the table (`gcp/backfill_ticker.py:134-161`, `:633-656`).

## Approaches considered

1. The table or an explicit answer, on every replay surface, held by a guard (chosen). It is the owner's rule and it matches what `/api/market/dates` already does. The status code tells an outage (503) from an answer (404), and the `detail` prefixes of Design 7 tell the 404 answers apart.

## Design

### 1. What "the table has bars for a replay of D" means

What each job a replay starts actually reads:

| Surface | Job | Reads for date D | Reads `market_data_intraday` |
|---|---|---|---|
| `/replay` | `premarket-brief`, `BRIEF_AS_OF=D` | daily rows dated before D (`gcp/premarket_brief.py:991-1008`, `:1357-1362`) and D's premarket snapshot on the daily row (`:1354`) | no |
| `/replay` | `insight-pipeline`, `INSIGHT_AS_OF` | `market_data_daily` (`lib/agents/summarizers.py:229`, `:609`) | no |
| `/replay`, cached | the two render-existing jobs | stored `premarket_analysis` and `insight_reports` rows | no |
| `POST /api/insights/report/{ticker}/refresh?as_of=` | `insight-pipeline` with `INSIGHT_AS_OF` through Cloud Tasks (`platform/api/routers/insights.py:876`, `gcp/insight_tasks.py:103-104`), or the same pipeline in-process (`insights.py:874`, `:881`, `:901-910`) | `market_data_daily`, as the row above | no; not gated here (Non-goals) |
| `/replay-signals` | `signal-replay` | stored `signal_alerts` | no |
| `/validate` | `validate-brief` | D's own session bars | yes, D |
| `/backtest` | `backtest` | the window asked | yes, the window (second spec) |
| `REPLAY_DATE` | `signal-monitor` replay | D's own bars (`scripts/replay_signal_monitor.py:101-127`) | yes, D; Discord does not start it |
| `PLAYBOOK_RESOLVE_DATE` | `premarket-playbook-resolver` | D's own regular-session bars (`gcp/premarket_playbook_resolver.py:470-480`), `no_bars` when there are none (`:481-483`) | yes, D; Discord does not start it |

- So `/replay` reads no 1-min bar. The brief and the insight replay the morning of D, from daily data before D. The check on the 1-min table is a coverage gate: is this ticker, around this day, something the nightly pull holds. The check on the daily table is the input check: is there a daily bar before D for the brief and the insight to read.
- Rule: the table has bars for a `/replay` of D when it holds at least one `1min` row for the ticker with `ts` in `[D - 7 days 00:00 UTC, D 00:00 UTC)`, and `market_data_daily` holds at least one row for the ticker with `date < D`.
- Why before D and not D itself: D's own bars are not an input; today's bars only land at 21:00 ET (`gcp/deploy.sh:4741`), and a Sunday date is a valid weekly brief (`gcp/premarket_brief.py:1296`) with no bars of its own. A D-itself rule would refuse both.
- Why raw UTC bounds: the table holds two timestamp conventions (CLAUDE.md 3.9). `D 00:00 UTC` is before any bar of D and after the regular session of D-1 in both.
- Why 7 days: it spans any weekend plus holidays.
- Why the daily check stays: it is the table `/replay` actually reads. On `main` a ticker with no daily row never reaches the brief; it runs the backfill (`gcp/discord_interactions/main.py:456-472`). With the backfill gone, a 1-min gate alone would dispatch a brief and an insight that have nothing to read.

### 2. Discord `/replay`

- New `replay_bars_in_table(ticker: str, d: date) -> bool` in `gcp/discord_interactions/main.py`. One query through `gcp.database.query_to_dataframe_strict` with `timeout_s=10`:
  `SELECT 1 FROM market_data_intraday WHERE ticker = :t AND interval = '1min' AND ts >= :lo AND ts < :hi LIMIT 1`.
  It raises when `is_cloud_sql_configured()` is False and lets a query error propagate.
- The window comes from `lib.eastern_time.replay_probe_window(d) -> (lo, hi)`, new, beside the helpers that read the table across the two conventions (`lib/eastern_time.py:187`).
- New `replay_daily_in_table(ticker: str, d: date) -> bool`, the strict replacement of `ticker_has_daily_data`: one query through the same strict helper with `timeout_s=10`:
  `SELECT 1 FROM market_data_daily WHERE ticker = :t AND date < :d LIMIT 1`.
  It raises when `is_cloud_sql_configured()` is False and lets a query error propagate.
- `handle_replay` runs the 1-min probe and then the daily probe, after the date parses and before the cached path:
  - 1-min probe False: reply `No replay for {T} on {D}: market_data_intraday has no 1-min bars for {T} in the 7 days before {D}. Nothing was fetched and no job was started.` Dispatch nothing; the daily probe does not run.
  - daily probe False: reply `No replay for {T} on {D}: market_data_daily has no daily bar for {T} before {D}. Nothing was fetched and no job was started.` Dispatch nothing.
  - either probe raises: log the exception, reply `Could not read {table} for {T}: the database did not answer. No job was started. Try again in a minute.` with the table of the probe that raised. Dispatch nothing. A statement timeout on a probe (`timeout_s=10`) takes this reply too.
  - both True: the cached path (`:422-450`) and the recompute path (`:474-513`) run as today.
- Removed: `ticker_has_daily_data`, `execute_cloud_run_job_blocking` (its only caller is the backfill, `:464`), the backfill block and `backfill_msg`.
- A ticker with exactly one daily row before D passes both probes and gets the brief's own `NO DATA` status: the brief needs two rows before D (`gcp/premarket_brief.py:991-994`, `:1004-1010`). On `main` a ticker with no daily row at all never saw that status, because the backfill ran instead.

### 3. `scripts/backfill_and_replay.py`

- Step 1 goes: `trigger_backfill_ticker`, `_month_groups`, `DAILY_HISTORY_DAYS` and the flags `--skip-backfill`, `--history-days`, `--include-news`, `--news-window-days`. argparse then rejects them, which is the loud answer.
- New `missing_replay_dates(conn, ticker, dates) -> list[tuple[date, str]]`: the same two probes per date on the script's own connection (`db_connect`, `:108`), the 1-min one with `replay_probe_window`. Each entry is a date and the table that lacks it. `main` opens the connection first, exits non-zero naming the ticker, the missing dates and their tables, and starts no job when the list is not empty. A query error propagates.
- `--skip-replay` stays and means "report only". The file keeps its name; the docstring says what it now does.

### 4. `_load_date_data` and `GET /api/market/data/{ticker}/{date}`

### 7. Response contract the frontend receives

On the four routes a 404 or 503 body is `{"detail": "<string>"}`, and solyra already reads `detail` as a string (`src/hooks/useMarketData.ts:42-43`, `src/hooks/useJournalChartTrades.ts:591`, `:764`). The other codes keep the shapes they have: a 422 from request validation carries a list in `detail` (`platform/api/main.py:121`), `replay-trades`' own 422 (`backtest.py:520-521`) and the 400 for a bad `end_time` (`platform/api/main.py:1015`) carry a string, and a 500 has no body contract.

| Endpoint | Not in the table | Database unavailable |
|---|---|---|
| `GET /api/market/data/{ticker}/{date}` | 404, `No 1-min bars for {T} on {date} in market_data_intraday.` | 503, `Could not read 1-min bars for {T} on {date}: the database is unavailable.` |
| `GET /api/market/reference/{ticker}/{date}` | 404, `No daily bar for {T} before {date} in market_data_daily.` | 503, `Could not read reference levels for {T} before {date}: the database is unavailable.` |
| `POST /api/backtest/replay-trades` | 200; each trade on that date is `{"id": ..., "status": "unavailable", "reason": "no bars for date"}` (unchanged) | 503, `Could not read 1-min bars for {T}: the database is unavailable.` or `Could not read journal trades for {T}: the database is unavailable.` |
| `POST /api/style/mine-and-validate` | 200; dates with no bars are left out of the mining, and if no profile clears: `{"status": "unavailable", "reason": "no condition profile cleared the mining threshold for either direction"}` (unchanged) | 503, same two texts |

- `{T}` is the ticker in upper case; `{date}` is the path value as sent.
- A 503 always means the read could not be made. A 404 does not always mean "not in the table", so the frontend tells the cases apart by the start of `detail`, never by the status alone:

| `detail` starts with | Status | Meaning | Routes |
|---|---|---|---|
| `No 1-min bars for ` | 404 | the table does not hold the ticker for that day or month | market data |
| `No daily bar for ` | 404 | the daily table holds no bar before the date | reference |
| `Invalid date ` | 404 | the path date is malformed | market data, reference |
| `No data for ` | 404 | the day is in the table but no bar is at or before `end_time` (`platform/api/main.py:1018`, text unchanged) | market data |
| `no matching trades found` | 404 | no journal trade matches the request (`backtest.py:553`, unchanged) | replay-trades |
| `Could not read ` | 503 | the database is unavailable | all four |
| `journal database not configured` | 503 | the journal has no database (`backtest.py:524`, `:703`, unchanged) | the two POST routes |

- The reference route's bucket branch keeps three 404 texts of its own (`Date {date} not found for {ticker}`, `No previous day available`, `No RTH data for {ticker} on {date}`; `platform/api/main.py:1184`, `:1188`, `:1222`), and the local-dev bars function has the `No 1-min parquet for ` text of Design 4. They exist only when Cloud SQL is not configured, never on a deployed service.
- The two POST routes never answer 404 for missing bars: that case is a 200 with `unavailable`, as the table says.
- The walk-forward history read of `mine-and-validate` is outside this contract (Design 6): a database error there is swallowed by the loader and the route can still answer 200 with a validated profile.
- A defect (not an outage) stays a 500. So does a statement timeout (SQLSTATE 57014): `lib.infra_errors` classes it as a query of ours running too long, not as the database being gone (`lib/infra_errors.py:487-489`), and a retry would not help. None of the four routes sets `timeout_s`, so it can only come from a server-side limit.
- `platform/api/schemas.py` gains `class ErrorDetail(ApiModel): detail: str`. The four routes declare `responses={404: {"model": ErrorDetail}, 503: {"model": ErrorDetail}}` (the two POST routes 503 only; the existing 400, 422 and `replay-trades` 404 are not added to the document here). `platform/api/openapi.json` is regenerated with `python scripts/export_openapi.py`.

## Risks

- A ticker with no bars on Discord. `/replay` for a ticker outside the nightly's set used to work after one to two minutes of backfill. It now answers at once that the table has no bars. The way in for 1-min bars is `/watchlist add`: both nightly pulls read the watchlist (`gcp/fetchers/fetch_alphavantage_intraday.py:45-52`, `gcp/fetchers/fetch_market_data.py:1220-1221`), from the first of the previous month onward. Older dates stay refused. The reply does not promise a date.
- How a new ticker gets its daily history now. `backfill-ticker` wrote up to 800 daily rows in the same command (`gcp/backfill_ticker.py:608`, `:620-630`). `/watchlist add` only inserts the `watchlists` row (`gcp/discord_interactions/main.py:602-676`). From there, by the code:
  - the nightly `fetch-market-data` (23:00 ET, `gcp/deploy.sh:4622`) writes one daily row a night for a watchlist ticker (`gcp/fetchers/fetch_market_data.py:1220-1224`, `:620-621`);
  - once one row exists, `fetch-earnings-history` (19:15 ET, `gcp/deploy.sh:4774`) picks the ticker up: it chains `_run_backfill()` (`gcp/fetchers/fetch_earnings_history.py:554-559`) with `BACKFILL_ALL_HISTORY=true` (`gcp/deploy.sh:2982`), whose targets include every ticker already in `market_data_daily` (`fetch_market_data.py:818-826`), and pulls the full daily series, cut to 10 years, for one under 1,500 bars (`:781-782`, `:902`). So the history should arrive on the first weekday evening after the first nightly row, with no operator. A failure of that chained step is logged and does not fail the job (`fetch_earnings_history.py:560-561`);
  - the operator's immediate path is `./gcp/deploy.sh backfill` (`gcp/deploy.sh:5399`, `:5094-5108`), which runs `scripts/backfill_watchlist_data.py` and pulls the full daily series for a watchlist ticker under 200 rows (`:107-112`, `:179-183`).
  This was read from the code and `gcp/deploy.sh`. The live schedulers and a real run were not checked for this revision. Until a daily row dated before D exists, `/replay` gives the daily reply; with one row, the brief's own `NO DATA`.
- The approved `docs/superpowers/specs/2026-11-13-feat-data-001-watched-ticker-ingest.md` is related but does not close that gap. Its job (not on `main`: `gcp/fetchers/fetch_watched_tickers.py` does not exist) pulls daily bars nightly for the tickers in solyra's per-user watched set (`:124-126`, `:155-177`). It never reads the `watchlists` table that `/watchlist add` writes (`:12`, `:302`) and fetches no minute bars (`:95-96`). So it gives a daily history to a ticker a web user watches, and that ticker still fails the 1-min probe unless it is also on the Discord watchlist.
- Tickers other than SPY, QQQ and IWM. On-demand onboarding through `/replay` ends for all of them. Charts, the scorecard and style mining already depended on the table for them; they lose only the bucket fall-through.
- Style validation can still run on bars that are not the table's. The walk-forward history read of `mine-and-validate` keeps `DataLoader`'s swallow and daily-bar fallback until the second spec (Design 6), and can write `user_style_results` and `playbook_cards_staging` from them. This spec does not reduce that risk; it stops it from spreading: `REPLAY_EXEMPT` holds that one function and `test_the_only_replay_exemption_is_the_style_history_loader` fails if a second is added or if the entry outlives the call.
- The web insight refresh with `as_of` is not gated the way Discord `/replay` is (Non-goals). It fetches nothing; the difference is only which surface refuses a ticker the table does not hold. The owner decides whether a later spec aligns them.
- Local development without Cloud SQL. The API keeps its bucket branch when Cloud SQL is not configured, so a laptop with bucket access still draws charts; the yearly daily file is gone there too. `/replay` and `scripts/backfill_and_replay.py` need a database and say so. `done_when` covers both API modes.
- A failed import of `gcp.database` no longer reads as local development on the two GET routes: they answer 503 (Design 4). The same reading remains on `GET /api/market/dates`, whose bucket path runs whenever `_CLOUD_SQL` is False (`platform/api/main.py:878`); this spec does not change that route.
- Reference levels lose the vendor's fresher answer. If the nightly daily fetch misses a day, the route returns the latest stored day, with `stale_days` set when the request is under 30 days old and that day is over 3 calendar days back; after a long weekend that flag can be set for a correct row. Nothing in solyra renders `stale_days` today. `done_when` pins the rule.
- The 7-day rule passes a date whose own day the table lacks (a gap day, or today before 21:00 ET). That is intended for `/replay`; `/validate` reads D itself and reports `NO INTRADAY DATA`.
- An outage now answers 503 where it answered 404 or 200, and what the site draws for it differs by reader. `useMarketData`, `useReviewQuote`, `useHistoricalDay`, the two POST hooks and the dashboard's reads throw on a non-OK response, so their query or mutation goes to its error state. `useReferenceLevels` (`src/hooks/useMarketData.ts:87`) and `PlaybookPage.tsx:77` return null on any non-OK response, so there a 503 is drawn as no reference levels, exactly as a 404 is today, until the solyra UI spec changes them. `tests/api/test_route_coverage.py` pins the new codes.
- solyra CI is red between this merge and the contract sync (Close-out 2). The solyra spec for the sync is approved before the merge so the window is one small PR long.
- A 404 is not one meaning. The frontend has to read the `detail` prefix (Design 7); a consumer that maps every 404 to "not in the table" would mislabel a malformed date, an `end_time` before the first bar and an unmatched trade request. The texts are pinned exactly in `done_when`.
- The reach test follows names inside one file. A fetch moved behind a new helper in another file is caught only when the helper itself holds the request or the registration test sees the new entry point. The limits are listed in Design 8.
- This spec narrows one sentence of the approved `docs/superpowers/specs/2026-10-12-feat-data-001-av-market-data.md` (`:467`: `_load_date_data` "SQL AND local/GCS fallbacks use the atomic guard/evidence contract"). With Cloud SQL configured there is no fallback left to guard. It does not supersede that spec: the gate allows `supersedes` only within one FEAT, that spec belongs to FEAT-DATA-001, no plan on `main` names it, and the two test files its `done_when` names for the replay routes (`tests/api/test_av_price_replay_routes.py`, `tests/scripts/test_av_price_replay_entrypoints.py`) do not exist.
