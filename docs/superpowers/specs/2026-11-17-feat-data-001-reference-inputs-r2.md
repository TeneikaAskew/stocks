## Rate storage and transaction boundary

Use three provider-specific SQL tables, rather than the initial proposal's ambiguous mixed header/body pair: `fred_rate_revisions` (durable capture intent and financial header), `fred_rate_payloads` (exact original response BYTEA plus canonical normalized observations), `fred_rate_publications` (immutable financial ACK). No new GCS namespace or lifecycle writer is required. The immutable SQL artifact identity identifies the exact payload row and capture UUID; do not manufacture a GCS generation or claim object-storage proof. Raw and normalized hashes remain distinct.

The revision header has a generated capture UUID, positive noncycling capture sequence, unique stable retry key (section "Execution identity"), exact DGS3MO request-window/configuration/code identity, state, admitted-at, nullable immutable intent-known-at, and once-bound actual response-completion/source identity, source/normalized hashes/byte counts and payload expiry. Operational reservations, failed/orphan states and narrowly checked body-removal receipt/ACK fields are distinguished from financial fields. Pending intent is not a financial revision. Bind financial identity once in the source transaction; after that all financial/header facts are immutable. Publish only validated full-response records, preserving missing observations. Runtime cannot forge intent clocks, financial bindings, publication or expiry evidence through direct DML. Owner-defined, pinned-search-path entrypoints implement exact transitions; no arbitrary SQL/callback/plugin interface or public administrative bypass.

The payload has a capture-ID PK/FK, immutable original entity bytes, canonical normalized rows, exact hashes/sizes and expiry. Store the original uncompressed HTTP entity bytes before JSON reserialization; hash precisely those retained bytes. No credentials occur in stored request identity. Metadata/publication can survive body deletion. Publication has revision-ID PK/FK, actual available_at and fixed acknowledgement-source kind; tuples cannot be updated/deleted by runtime. `daily_rates` remains a mutable cache and is expressly outside the immutable-tuple prohibition.

One real connection owns the financial transaction. A connection-taking batch helper in `gcp/fred_rate_publication.py` inserts the payload, binds the financial revision, and conditionally upserts the existing `daily_rates` cache in the same transaction. It must not wrap existing `upsert_dataframe`, which owns independent transactions (each chunk is its own committed transaction, `gcp/database.py:496-505`). Cache updates follow actual source-capture precedence; an older response acknowledging late cannot overwrite newer data. Equal capture clocks with different content are unavailable, not UUID-ordered winners.

The four bounded phases are: (1) atomic admission/pre-source recovery lookup plus eligible cleanup; (2) intent acknowledgement at the real later server clock, and eligible prior-removal ACK; (3) full source/header/payload/cache transaction; (4) financial post-COMMIT ACK and reservation finalization. The authoritative terminal is a structured log emitted only after the actual phase 4 response and bounded cleanup, with no additional database exchange or job_runs write. Earlier refusal/error paths also emit their actual structured terminal after bounded cleanup; no unpriced terminal SQL is added. Use a dedicated low-level pg8000 DBAPI connection with its public autocommit=True, obtained through the public Cloud SQL Connector connect API (or explicit loopback pg8000 connection in local tests). DATA owns this bounded connection factory inside `gcp/fred_rate_publication.py`; retain the same configured instance/database/user/credential selection and lazy connector refresh (`gcp/database.py:159-169`), with explicit remaining-time limits and closure. Do not extract private SQLAlchemy pool hooks or change the shared engine. Each phase uses the supported public cursor.execute(operation) simple-query path with no parameter arguments or stream, as one fixed function statement in a single atomic implicit server transaction. Parameterized pg8000 execute_unnamed is excluded because its Parse/Describe/Bind exchanges would exceed the eight-interaction budget. Only the fixed qualified owner function name and SQL template may form SQL syntax. Canonical UTF8 JSON descriptor bytes, including bounded original entity bytes encoded as base64 when required, are converted using bytes.hex() to lowercase hex, strictly validated as [0-9a-f] and decoded server-side into the fixed typed envelope. No raw external text, identifier, function name or SQL fragment is interpolated. Cap the full JSON envelope before encoding at 2 MiB, the hex SQL operation at 4 MiB plus 256 fixed template bytes, and new transient transport buffers at 16 MiB; reject overflow before building or sending the operation. The retained raw 1 MiB / normalized 64 KiB / metadata 64 KiB caps remain independent. Tests include adversarial quotes, backslashes, Unicode and binary entity bytes, exact hash/round-trip validation, oversized envelopes and credentials absent from SQL/error logs. Never log the operation or body. Actual simple-protocol flush/receive evidence, not merely one Python execute call, is required. Its successfully completed idle ReadyForQuery response is the actual transaction acknowledgement; only a later independent phase records its ACK clock. No explicit no-op COMMIT or implicit client BEGIN is issued. At most 8 total actual database interactions are allowed: four phase statements and at most four startup/authentication/protocol/initialization interactions. Count cold startup and recovery as well as queries; connector authentication work is independently timed and charged. No hidden pre-ping, dialect/reflection, per-observation or metadata query is allowed. An early actual-pg8000 cold-driver proof must establish this composition within 8 before the ready plan can progress to full writer cutover; source inspection or a mocked execute counter is insufficient. A failed/denied branch may finish earlier. If actual driver composition cannot meet this bound, activation is refused; do not silently omit acknowledgement or increase the bound.

The intent transaction commits first; phase 2 captures only the actual later server clock, and vendor work starts only after that phase commits successfully. A lost intent ACK is uncertain and fails closed. Server-derived transaction provenance must reject intent, financial or removal ACK in the same outer transaction, including open/released/nested savepoints; tuple xmin inequality alone is not commit evidence. Capture source/cache commits before financial publication; phase 4 uses the actual later server clock. Never substitute source date, fetched_at, transaction start or cache update for either ACK. Tests kill the actual producer after each commit and before its ACK. Unknown commit outcomes require bounded exact-identity reconciliation; no presumed success or new vendor call.

## Execution identity

The unique first lookup identity is the fixed job (`fetch-fred-rates`) plus native execution/task identity, excluding retry attempt number, request window and code/configuration. Perform that lookup before evaluating moving date defaults. Freeze the initially resolved bounded window, code/configuration and explicit CLI arguments in its durable intent. A retry reuses the stored window across UTC/local midnight; explicitly supplied mismatches or changed code/configuration refuse rather than generate a new key. Only a genuinely new execution identity may resolve fresh defaults and create an intent. A manual fresh invocation needs a new explicit execution identity.

The identity comes from exactly one of two inputs, resolved before any vendor, archive, maintenance, financial or database I/O:

- **Cloud Run.** When the environment variable `CLOUD_RUN_EXECUTION` is set and nonempty: kind `cloud_run`, value `CLOUD_RUN_EXECUTION`, task index `CLOUD_RUN_TASK_INDEX` (0 when unset). `CLOUD_RUN_TASK_ATTEMPT` is never part of it, so the job's one platform retry (max-retries 1) finds the same intent. Every Scheduler run and every `gcloud run jobs execute fetch-fred-rates` is a new Cloud Run execution, so a manual run on Cloud Run gets a new identity without an option.
- **Outside Cloud Run.** The new option `--execution-id <id>`: kind `manual`, task index 0. The value must match `^[a-z0-9][a-z0-9-]{7,62}$` (8 to 63 characters of lowercase letters, digits and hyphens; a lowercase UUID fits). The operator reuses a value only to retry that same manual run.

The kind is part of the unique key, so a manual value never matches a Cloud Run execution name. No identity is generated: a random value would let a retry miss its committed capture and call the vendor again, and a NULL or constant would make separate manual runs collide (the run id of `gcp/bar_recompute.py:85-94`, `local-<UTC timestamp>`, has the first defect, two calls a second apart outside Cloud Run returning two ids, and is not reused). Refusals exit 2 with a controlled terminal, zero vendor calls and zero database interactions:

- `execution_identity_missing`: apply mode with neither input.
- `execution_identity_conflict`: both inputs present (an operator cannot relabel a Cloud Run execution).
- `execution_identity_invalid`: an `--execution-id` value that fails the pattern.

Once resolved, the phase 1 lookup decides:

- **Distinct** (no intent holds the key): resolve defaults, admit and charge a new intent; one source call.
- **Reused with the same frozen arguments, configuration and code:** an acknowledged capture is a verified already-ACK recovery with zero source calls and a healthy terminal; a capture whose source committed without its financial ACK resumes exactly that capture at the actual later recovery clock, with zero source calls; a pending/failed/orphan capture with no coherent committed body remains unavailable and charged, nonzero, with zero source calls. It cannot silently refetch under the same key.
- **Reused with different explicit arguments** (for example another `--start`) **or changed configuration/code:** refused with `execution_identity_reused`, nonzero, zero source calls.

A `--resume-capture <uuid>` can only recover that exact stored capture and cannot start a source call; it admits no intent, so it refuses `--execution-id`, `--start`, `--end` and `--backfill` (exit 2). `--dry-run` accepts either identity input and, given one, performs the phase 1 lookup read-only and reports the outcome apply mode would take; given neither it plans a fresh admission. It writes nothing in any case. An actually new admitted invocation creates a new intent and charge.

## Response window binding

FRED's JSON observations response echoes its request. One DGS3MO request for 2025-11-05 to 2025-11-14, made 2026-11-17 to read the shape, returned top-level `realtime_start` and `realtime_end` (both 2026-11-17), `observation_start` 2025-11-05, `observation_end` 2025-11-14, `units` `lin`, `output_type` 1, `file_type` `json`, `order_by` `observation_date`, `sort_order` `asc`, `count` 8, `offset` 0 and `limit` 100000, then 8 observations of `realtime_start`, `realtime_end`, `date` and `value`, the 2025-11-11 value `'.'`.

The request sends `observation_start` and `observation_end` from the frozen window, and `units=lin`, explicitly. Before normalization the producer accepts a response only when:

- `observation_start` and `observation_end` equal the frozen window exactly;
- `units` is `lin` (the percent units the division by 100 assumes);
- `offset` is 0 and `count` equals the length of `observations` (one complete page, at most 32 under the existing cap);
- every observation `date` lies inside the frozen window, inclusive.

Anything else fails the whole response with `error_class` `source_window_mismatch`: no financial publication, unchanged cache, a failed charged capture and a controlled nonzero terminal. A response is never trimmed to the window. `realtime_start`/`realtime_end` are recorded in the capture provenance as FRED's reported vintage dates and never become a knowledge clock. The selector also refuses any stored observation dated outside its capture's frozen window, so no capture qualifies a date it was not asked for.

## Missing values and candidate ordering

Normalize every valid dated FRED observation. Preserve `'.'` as status=missing, value=NULL, original token, observation date, source units=percent_per_annum and normalized units=ratio_per_annum. Preserve valid numeric zero. Convert exact finite decimal percent by 100 without binary-float loss. A syntactically valid observations=[] response is a nonzero source failure with zero financial publication and unchanged cache; it is not validated-empty success. Preserve this distinct case from one or more valid dated missing-value rows. Duplicate conflicting dates, malformed dates, nonfinite/unparsable financial tokens, invalid shape, overflow or truncation fail the whole response with a controlled nonzero terminal outcome. Transport errors are diagnostics, not validated-empty financial snapshots. Never reuse the old dropna/coerce-to-empty success path. Missing-status observations do not overwrite a measured cache value with zero; the immutable selector still reports their unavailability.

Both modes select within exact provider/ticker/window scope, then evaluate the selected candidate's status, actual ACK, retained body, hash, units and freshness. They never filter numeric-valid/published candidates before ranking. Strict mode excludes confirmed captures after as_of and requires all known_at clocks at/before it. Confirmed future intents do not block an earlier eligible cutoff; an uncertain intent clock conservatively returns unavailable until reconciled. Pending/newer applicable evidence blocks older numeric fallback. Recovery ACK ordering never changes source-capture precedence. Equal source clocks with incompatible content return unavailable.

For rates, choose the latest applicable response capture covering the requested session, then the greatest observation date not after that NYSE session within that exact response. NYSE sessions resolve through `lib.eastern_time` (`is_session`, `latest_session_on_or_before`, `lib/eastern_time.py:728`, `:764`). Current mode additionally requires actual acknowledged evidence at the supplied aware current-analysis time; it does not confer PIT validity.

Percent-suffixed or otherwise incompatible units are unavailable, never heuristically divided based on magnitude.
