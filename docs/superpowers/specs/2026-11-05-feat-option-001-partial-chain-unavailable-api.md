# Partial options chains are unavailable through lib and every options route

## Decision and lineage

This specification is the first half of the bounded gamma-chain repair the owner approved on
October 13, 2026 ("Fix it") and first specified in PR #1490 as one contract. On November 5, 2026
the owner decided to deliver that repair as two parts: this part (unavailable semantics through
`lib/` and the options API, with strict-prior snapshot selection) and the collector-and-recovery
part (`docs/superpowers/specs/2026-11-05-feat-option-001-chain-collector-recovery.md`). Together
the two carry every requirement, every original `done_when` item and every amendment the first
Codex review of #1490 asked for; nothing is dropped. The owner also approved the public chain
field names `sides_present` and `chain_state` (the earlier open choice X6). This part writes no
production data and changes no collector.

## Problem

At 2026-10-09 01:01 UTC the EOD collector stored calls-only October 8 chains for SPY (6,580
contracts) and IWM (2,874) and reported success. Every options surface then treated the stored
one-sided chain as measured data: `GET /api/options/{ticker}/{date}` returns it as a successful
`OptionsChainResponse` with only `metadata.row_count`; `POST /api/options/greeks` accepts it and
emits numeric GEX, VEX and a put/call ratio of `0.0` (`lib/gamma.py` divides a zero put open
interest by the call open interest); `GET .../levels`, `.../grid` and `.../nodes` compute a
regime and totals from one side because the `greeks_coverage` gate detects missing gamma values,
not a missing side. A `0.0` or a one-sided total presented as measured data is the fabricated
value REQ-DATA-001 forbids. Separately, the feature builder's shift-join on the dates present in
`gamma_levels_eod` loses a valid prior snapshot when the current day's snapshot is absent, and it
admits whatever stored date precedes the bar rather than a date strictly before it.

## Design

1. **Side completeness in `lib/gamma.py`.** `build_summary` and `build_grid_summary` share one
   check: a chain with no calls or no puts is partial. For a partial chain they return regime
   `unknown`, `total_gex`, `total_vex`, `gamma_balance` and `gamma_flip` as `None`, an explicit
   warning naming the missing side, and the spot estimate when it is independently available
   (parity needs both sides and is skipped; the delta and median-strike methods still apply).
   Existing sign conventions, the GEX multiplier and the Black-Scholes crossing search are
   unchanged; a complete chain can legitimately have no crossing and keeps `gamma_flip = None`
   with its existing warning, not the partial-chain warning.
2. **Chain route.** `GET /api/options/{ticker}/{date}` adds `metadata.sides_present`
   (`"both" | "calls_only" | "puts_only"`) computed from the selected rows, and for a one-sided
   chain adds top-level `chain_state: "unavailable"` with a `reason`; a both-sided chain carries
   `chain_state: "available"` and no reason. The rows are kept in both states so the client can
   show what was stored. `GET /api/options/live/{ticker}/{date_str}` normalises provider rows
   itself and shares `OptionsChainResponse`; it applies the same side check to its normalised
   rows and carries the same `metadata.sides_present` and `chain_state`. Both fields are
   declared on the shared schema with no server-side default, so neither route can omit them,
   and ASGI tests cover complete and partial chains on both routes. The response's
   `snapshot_timestamp` and the chain cache behaviour are unchanged; `snapshot_provenance`
   (the separate approved labels specification) is unaffected.
3. **Greeks route.** `POST /api/options/greeks` applies the same side check before any
   aggregation. For a one-sided or empty chain it returns `metrics.total_gex`, `total_vex` and
   `put_call_ratio` as `null` with a `reason`, and empty `aggregated`, `gex_by_strike` and
   `nodes`; the three metric fields become nullable in `platform/api/schemas.py`. The current
   `0.0` totals and `0.0` put/call ratio for a degenerate input are removed, not relabelled.
4. **Levels, grid and nodes.** `GET .../levels` inherits the chain's state through the shared
   loader and returns the `lib` result (unknown regime, null totals, the warning). `GET .../grid`
   and `GET .../nodes` return the same from `build_grid_summary`; `total_gex` and `total_vex`
   on `GammaGridResponse` and `GammaNodesResponse` become nullable, and the existing unavailable
   envelopes carry `null` instead of `0.0` for those two fields. No source-selector, freshness or
   cache-policy change.
5. **Strict-prior, NULL-preserving snapshot selection.** The feature builder selects the latest
   gamma snapshot whose date is strictly before the bar date, independently of whether the bar
   date itself has a snapshot, and carries that snapshot's values as stored, including a `NULL`
   `gamma_flip`; it never searches further back for a non-null flip, never reads a same-day or
   later snapshot, and never fills past a present unavailable row (the marker rows the recovery
   part writes). A missing prior snapshot leaves the gamma context columns `NaN`, never `0`.
   The change is confined to the shift-join selection in `gcp/research/strat_engine/strat_data_builder.py`
   and `gcp/research/p7_build_multi_tf_features.py`; those files belong to the STRAT lane, so
   the edit is coordinated with that lane's open work and limited to the selection.
6. **Contract.** `platform/api/openapi.json` is regenerated only through `scripts/export_openapi.py`.
   The solyra consumer re-syncs the contract and renders `chain_state`, `sides_present` and the
   null metrics as unavailable states under its own approved specification; deployed-site proof
   is the owner's close-out step per AGENTS.md.

## Non-goals

No change to GEX, VEX, flip or balance formulas or sign conventions; no new eligibility
threshold, source selector, cache policy or provider call; no collector, cursor, marker-writing,
ledger or recovery change (those are the second part); no production data write; no deployment
claim. Issues #812, #871, #876, #878 and #896 stay separately decided.

## Verification

Each `done_when` item needs failing fixtures on the baseline before implementation and passing
fixtures after. The baseline numerics for both-sided fixtures are captured from `main` and
pinned in the test modules so compatibility is proved against numbers, not against the code
under test; byte equality is asserted over the pre-existing fields, and the new fields are
asserted on their own. Direct and ASGI tests cover every route named above; the strict-prior fixture runs in
the real-SQL harness (`tests/integration/`). The chain fixture used by the first review's finding
(stored calls-only SPY and IWM October 8 rows) is reproduced synthetically; stored-row counts in
production are not claimed here.

## Capacity

- Volume: 0 new rows read or written. The side check runs over the rows the existing statements
  already select (about 5K contracts per chain).
- Velocity: 0 additional SQL statements, 0 provider calls, 0 network round trips.
- Wall-clock: one pass over the selected rows' `option_type` column (sub-millisecond at 5K rows)
  on the request path; no Cloud Run job, scheduler or task-timeout change.
- Cost: $0 per run × 0 runs/day × 30 = $0/month.

## Delivery and close-out

The implementation branch uses this immutable main-approved specification and one ready plan
(`feature/feat-option-001-partial-chain-unavailable-api`), opened only after this specification
is on `main`. Existing protected files, pins and specifications remain untouched. The collector
and recovery part follows in its own branch and rebases onto whichever of the two lands second
where they share `platform/api/schemas.py` and `platform/api/openapi.json`. The historical gap is
not issue-wide options or UI remediation completion.
