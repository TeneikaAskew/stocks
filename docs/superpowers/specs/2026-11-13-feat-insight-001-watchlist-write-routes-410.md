# Lock the default watchlist to Discord and the CLI, stage B: the two web write routes answer 410

## Authority and status

Supersedes `docs/superpowers/specs/2026-11-13-feat-insight-001-watchlist-default-lock.md` together with stage A
(`2026-11-13-feat-insight-001-watchlist-default-lock-a.md`), which carries the read side, the ranker
and the readers. This stage is the one piece the owner gated on 2026-11-13: "the 410 switch on the two
web write routes ships only after solyra no longer calls them and that is verified on the live site."
The wording is the approved text of the lock spec; what is new is the live-site precondition. The
owner approves it by merging the PR that adds it.

## Problem

`POST /api/insights/watchlist/add` and `DELETE /api/insights/watchlist/{ticker}`
(`platform/api/routers/insights.py:599-701`) write the caller's own rows into the stocks `watchlists`
table through `gcp.fetchers._watchlist.add_to_watchlist` and `remove_from_watchlist`. No job reads
those rows, and in `open` mode the owner resolves to `'default'`, so a web add edits the universe
every job reads (stage A, Problem items 1 and 3). The add route also fabricates an empty list on a
failed read-back (#1329, `insights.py:639-643`). Solyra's per-user watchlist (its spec v2) replaces
every call to these routes; once it is deployed, the routes have no caller and the write path closes.

## Non-goals

- No removal of the two routes from the router here: they stay declared and answer 410 so solyra's
  contract test keeps passing against the vendored OpenAPI; their deletion is its own small spec once
  solyra's change has been on main for a while (owner's decision 3).
- No change to Discord `/watchlist`, the CLI, the seed, or any reader.

## Design

Both routes answer `410 Gone` with detail
`The watchlist is managed in Discord (/watchlist add, /watchlist remove); the web app keeps per-user lists in solyra.`
for every caller, signed in or open mode, and write nothing: the handlers raise `HTTPException(410, detail)`
before touching either database path, `_watchlist_owner` (`insights.py:57`) is deleted, and the router imports
nothing from `gcp.fetchers._watchlist`, so no write can reach the table from the API process. The two
helpers the routes call today open their own DB-API connection through `lib.agents.model_routing.connect()`
(`gcp/fetchers/_watchlist.py:521` and `:571`), not `gcp.database.get_engine`, which is why the no-write
test below records both. The
response models `WatchlistAddResponse` (`insights.py:535`) and `WatchlistRemoveResponse`
(`platform/api/schemas.py:1468`) stay declared so the operations stay in the OpenAPI document, which
gains the 410 response on both (`responses={410: ...}` on the decorators).

### Live-site precondition

Before this PR is marked ready, the implementer runs, read-only:

```
env -u CLOUDSDK_AUTH_ACCESS_TOKEN gcloud logging read \
  'resource.type="cloud_run_revision" AND resource.labels.service_name="solyra-api-staging"
   AND (httpRequest.requestUrl:"/api/insights/watchlist/add"
        OR (httpRequest.requestMethod="DELETE" AND httpRequest.requestUrl:"/api/insights/watchlist/"))' \
  --project=adept-mountain-474619-d4 --freshness=48h --limit=50 \
  --format='table(timestamp, httpRequest.requestMethod, httpRequest.requestUrl, httpRequest.status)'
```

over a window that starts after solyra's deploy and spans at least one full trading day. Zero rows is
the precondition; any row names a caller still using the routes, and the switch waits.

### Tests

`tests/api/test_watchlist_default_lock.py` gains the 410 tests: a signed-in firebase caller
(`monkeypatch.setattr(api.auth, "AUTH_MODE", "firebase")` with `_verify_bearer_email` stubbed, as
`tests/api/test_platform_auth.py:33` does) and an open-mode caller both get 410 with the detail, and two
recorders see no INSERT and no UPDATE: one patched beneath `gcp.database.get_engine`, one patched at
`lib.agents.model_routing.connect` (the path the two helpers use), each a fake connection whose
`cursor().execute` appends to a list the test asserts empty. Run against origin/main the same test fails,
because today's handlers reach `connect()` through `add_to_watchlist` and `remove_from_watchlist`.
`tests/gcp/test_watchlist_readers_default_owner.py` drops the stage A exclusion. The snapshot test
`tests/api/test_openapi_snapshot.py` passes on the regenerated document.

## Cross-repo contract

After this stage the web writes nothing to stocks. Solyra's per-user list lives in its Supabase
project; the only per-user data reaching stocks is `extras` on one ranker request and the owner-free
set the nightly ingest job reads (stocks spec `2026-11-13-feat-data-001-watched-ticker-ingest.md`).

## Risks

- A client other than solyra still calls the routes: it gets an honest 410 with the detail naming
  Discord; the precondition's log read is what shows whether such a client exists.
- The log read misses a caller because the window was short: the done_when requires at least one full
  trading day after solyra's deploy, and the implementer pastes the window.

## Decisions (owner, 2026-11-13)

1. Block now, delete later (decision 3 of the lock spec).
2. The switch ships only after solyra no longer calls the routes and the live site shows it; everything
   else landed in stage A.
