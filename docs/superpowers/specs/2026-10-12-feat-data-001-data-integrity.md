# Source ingestion integrity and bounded data repair

## Approval and scope

Approved repair scope: [GCP repair review](https://chatgpt.com/space/page_531ea2540b4c8191a4e5267eb24f1b89). On 2026-10-12 the user directed, “Execute the plan with test driven development.” This spec records that previously approved repair scope; it does not claim fresh approval of additional features. Approval covers implementation and tests of these repairs, not an assertion that a provider credential or unverified endpoint works. Spec publication precedes implementation.

## Problem

The 2026-10-12 review compared production SQL, job logs, deployed API schemas/handler contracts and direct provider responses against stocks `17bbacd371843963a3d7983589ffc8c825664675`. Evidence was collected read-only in `work/gcp-review/evidence-package.json` in the review workspace. The implementation must promote redacted minimal fixtures into the repository; this local evidence path is an audit locator, not a runtime dependency.

October 8 IWM has 2,874 calls and no puts; the verified refetch has 2,874 of each. SPY has 6,580 calls and no puts; refetch has 6,580 of each. QQQ's 5,721 calls and 5,721 puts is a control. The existing `LIMIT 1` skip treats partial partitions as complete. Shared gamma code accepts them and changes sign on the repaired inputs. Benzinga accepts token query authentication and nested date parameters, but current code adds a failing Authorization header, uses ignored top-level dates, drops source IDs, collapses 58 US macro rows to two cache identities and filters them all out for IWM. Earnings are clamped to seven days despite the consumer's fourteen-day range. AV returned empty insider data even for AAPL; SEC submissions independently showed recent Form 4 filings. Current successful-job status does not establish source completeness. Quote endpoints default to an EOD provider contract.

Catalog row: `FEAT-DATA-001 | Data platform | Ingestion, storage, freshness`. This is the owning capability; catalog wording and canonical requirement definitions remain unchanged in the spec phase. Open issues touched: stocks#1259, #1260, #1302, #1303, #1365. Closure requires full issue DoD verification, not just a cross-reference. Other symptoms are evidence-led repairs, not invented issue IDs.

## Non-goals

No model promotion, trading strategy threshold calibration, broker execution, unrelated API/UI redesign, blanket multi-year rewrite, or unrelated scheduled workload. Do not claim EW access has recovered without authenticated content. Do not promise vendor completeness, fresh quotes from an EOD entitlement, or complete ETF constituents from a top-holdings response. Do not change catalog capability definitions or canonical requirements.

## Approaches considered

1. Rerun jobs unchanged: rejected because skip-existing, identity collisions and silent empty-success remain.
2. Replace providers and rebuild all history: rejected because contracts, cost and point-in-time provenance are not established.
3. Repair verified adapters, share validity and receipt contracts, and regenerate only explicitly affected partitions: selected in the approved review.

## Design

### A. Source receipts and temporal integrity

Create `lib/source_receipts.py`, with immutable `SourceReceipt` and `SourceHealth` models; persistence in `gcp/source_receipts.py`; additive canonical schema in `gcp/schema.sql`, applied by the existing default `gcp/apply_schema.py`/API deploy path, with `gcp/queries/source_integrity_schema.sql` as a companion review artifact only. Test the actual applier against isolated PostgreSQL twice; readers cannot deploy before those tables/columns exist. Do not alter gate/trigger governance. Reuse existing database and shared exchange-calendar utilities. Centralize current-facing read decisions here rather than adding unrelated age heuristics to every consumer.

`SourceReceipt` fields: `run_id`, `source`, `dataset`, `partition_key`, `status` (`complete|partial|empty|failed|unavailable`), `requested_from`, `requested_to`, `observed_at`, `available_at`, `fetched_at`, `completed_at`, `rows_received`, `rows_valid`, `rows_written`, `rejected_count`, `watermark`, `error_class`, `http_error` (redacted endpoint, method, status), `reason`, `coverage` and `revision_id`, `attempted_calls`, `successful_calls`, `raw_receipt_uri`, `raw_payload_hash`, `rejection_reasons`, `field_completeness`, `latest_successful_fetch`, `effective_session_date` and `downstream_status`. Extend existing `job_runs` telemetry where possible; a receipt is a source/partition child of that run, not a competing definition of success. Retain redacted raw receipts or a content-addressed reference under the existing artifact policy so a future one-sided chain can be traced before versus after normalization. Timestamps are timezone-aware UTC or null; source-provided dates retain their precision metadata. Coverage describes requested and achieved ranges plus selected/processed/deferred ticker counts, never infers coverage from MAX(date). `observed_at` is the event/snapshot time, `available_at` is the earliest provable availability of this exact version to this system, and `fetched_at` is transport time. A freshly fetched old quote is old. Unknown historical availability stays unknown; do not backdate repaired values to manufacture replay eligibility. An event scheduled for a future date can be known before cutoff; its released actual value needs its own availability/version.

`assess_source(receipt: SourceReceipt | None, *, now: datetime, cutoff: datetime | None, policy: FreshnessPolicy) -> SourceHealth` returns status (`current|stale|partial|empty|failed|unavailable`), reason, source clocks, coverage and recovery instruction. `eligible_at(observed_at: datetime | None, available_at: datetime | None, cutoff: datetime) -> bool` is for realized observations only; requires both known and no later than cutoff. Scheduled event metadata uses `available_at <= cutoff` independently of future event time. Missing clocks never mean current. Per-dataset policies declare owner, cadence, threshold and recovery; preserve existing exchange-session rules for EOD and established gamma age tiers. Record partial/failed sources even if another source succeeds. Writes and receipts are idempotent by run/source/partition; publish success only after the data transaction commits. Retain last-good values with stale provenance on later failures.

### B. Options validity and recent repair

Create `lib/options_integrity.py`: `validate_chain(rows: DataFrame, *, ticker: str, session_date: date) -> ChainValidation` checks identity/date consistency, duplicates, supported option sides, nonnegative finite OI and finite Greeks where required by the consumer. Completeness requires both calls and puts with usable contracts; equal side counts are not required. Side presence is necessary, not a claim that every listed contract is present. All-zero/missing required Greeks are separately unavailable for gamma. Failed input has a reason and cannot publish directional gamma or synthetic zero totals.

Use the same validator from `gcp/fetchers/fetch_av_historical_options.py`, `gcp/research/p2_build_gamma_levels.py`, `lib/gamma.py` entry points, `lib/agents/summarizers.py`, and `platform/api/routers/options.py`. Skip-existing consults validated receipts/partition statistics rather than existence of one row. `--from-latest` revisits the last **5 exchange sessions** by default, inclusive of the newest completed session, to catch a recent hole behind the high watermark; an explicit date range remains available. Bound provider retries to existing approved limits and show partial terminal status.

Stage and validate the complete replacement for one `(ticker, snapshot_date, data_source, market_session)` partition before an atomic publish; no intermediate calls-only partition is current. Do not delete last-good data when refetch fails. A repair manifest contains exact partitions, before/after counts by side, payload hashes, code version and receipt IDs; §L pins the signed numerical oracle and surface-specific tolerances. Initial explicit target is `IWM,SPY` on `2026-10-08`; QQQ is a no-op control. Provider refetch is a later revision: preserve original observation versions/audit references and prevent it appearing as known on October 8.

Unknown unit/measure is unknown, not an inferred percent. Identity is source + event ID + provider revision/content hash, with separate stable event identity; preserve historical revisions. FRED dates remain schedule evidence; existing canonical release times are labeled inferred schedule times, not measured release timestamps.

Summarizers expose actual, consensus and prior only with compatible measure/unit/period; an unmapped series remains distinct/unavailable, not silently merged.

### F. Insider universe and SEC fallback

Avoid double counting overlapping providers where identity is unproven by keeping source-separated records and selecting one provenance-marked view.

### J. Completion-gated dependencies and postrelease refresh

## Risks

Vendor pagination can truncate a plausible range; receipts retain partial state. Corporate-action/option adjustments can create unequal side counts; validation does not require equality. Late revisions could leak into replay; both clocks and version eligibility guard the read path. XML amendments and duplicated AV/SEC records could overstate buying; explicit source precedence and accession identity are tested. Larger earnings windows can explode enrichment calls; enrichment remains separately bounded. Additive health metadata needs serializer/schema tests to avoid silently dropping fields. Operational provider outages can remain degraded after successful code repair; the acceptance claim is truthful behavior, not a fabricated external recovery.
