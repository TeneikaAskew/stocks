## Problem

The reviewed production IWM report says a strong directional thesis while its final deterministic conviction is low. `lib/agents/orchestrator.py` calibrates conviction and replaces numeric plans after the portfolio-manager narrative has already been written. Its planner failure branch still copies LLM prices; trader/manager failures also synthesize confidence. The October 8 fixture uses close 277.7, ATR 3.7368433430628203 and a distant previous-year trigger 171.73, yet presents entry/stop/targets as an actionable plan while its rationale asks for ORB confirmation. These are reproducible contract inconsistencies, not evidence that a new trading strategy works.

Evidence: the approved review, `work/gcp-review/planner-reproduction.json`, `deep-results.json` and the inspected report API schema/handler (protected endpoint probes returned 403; a current authenticated payload was not independently verified), based on stocks `17bbacd371843963a3d7983589ffc8c825664675`. Promote sanitized fixture excerpts into tests during implementation. Catalog row: `FEAT-INSIGHT-001 | AI insights | LLM per-ticker reports + chat`. Touches stocks#1295 (failed trader/manager output); the broader stocks#1217 replay defect is a dependency/context, not a claim this limited spec closes every replay path. The data integrity spec supplies source metadata; this spec consumes it after publication without editing that spec or catalog capability definitions.

## Non-goals

No calibration-threshold retuning, new entry strategy, forced bullish/bearish interpretation, model promotion, report-history rewrite, or unrelated chat overhaul. Do not turn a failure into a neutral recommendation. Do not claim that a generated confidence score is a measured probability. Preserve valid existing deterministic recipes; repair the publication contract. Respect the independently approved FEAT-CATALYST-001 spec on main (PR1419): earnings-history/news/source financial ingestion remains owned there; this report repair consumes merged source contracts and does not duplicate those algorithms or archival/version stores.

## Approaches considered

1. Prompt-only warnings: rejected because post-generation calibration still changes the published decision.
2. Replace the planner or retune thresholds: rejected; the approved issue is truthful representation of known deterministic output.
3. Finalize deterministic decision facts before publication, constrain the narrative to them and represent pending/unavailable plans explicitly: selected.

## Design

### A. Final decision contract

Add `lib/agents/report_consistency.py` with `DecisionFacts` (final direction, calibrated conviction, nullable model confidence, confidence provenance, plan state, deterministic plan, source receipt references, failed sections and reasons). `finalize_decision(*, direction: str, conviction: str, confidence_score: float | None, plans: list[PersonaPlan], failed_sections: list[str], failed_section_reasons: dict[str, str], source_status: list[dict]) -> DecisionFacts` composes final facts without inventing financial values. Build the canonical public failure-reason mapping once at capture using §D controlled stage/error-class/stable-code rules, then preserve that exact sanitized mapping through DecisionFacts, persisted report JSON and API/Discord. Raw exception strings are not this public mapping; no existing sanitizer is assumed. Do not reconstruct reasons later from section names or invent a different downstream classification. Keep the existing `_calibrate_conviction` rules and thresholds. Missing calibration inputs remain unavailable and are recorded; never substitute FTFC 0 or synthetic confidence 0.3 merely to make calibration succeed. Expose nullable `calibrated_conviction` and `conviction_status=unavailable` for unknown calibration. Widen final `conviction` to nullable rather than storing an invented low/neutral placeholder; legacy complete reports retain their original enum values.

Update `lib/agents/schema.py` with additive `plan_status` (`ready|pending_confirmation|invalidated|unavailable|not_applicable`), `plan_reason`, `confirmation_requirement`, nullable `candidate_trigger` (context only), `invalidation_observation` (nullable reserved compatibility metadata, never fabricated by this repair), `conviction_status`, `decision_provenance`, `confidence_kind` (`model_score|unavailable`) and source-health metadata on final reports/persona plans. No field promises a calibrated probability. Keep existing route names and valid-response field names. For **every newly generated non-ready plan** (`pending_confirmation`, `invalidated`, `unavailable`, `not_applicable`), final headline and persona output has `entry_zone=null`, `stop=null`, `targets=[]` and all executable position-sizing/risk/reward metrics null. Only `ready` may carry executable numbers. Apply this invariant in finalization before persistence and again at API/Discord serialization; a frontend hiding prices is insufficient. Clear nested/stale numeric values inherited from earlier drafts. Source key_levels and labeled candidate_trigger may remain non-executable context with source/time, not be copied into trade fields. This does not rewrite complete legacy historical records merely because their optional new status is absent. This is an explicit schema widening needed to remove fabricated prices; complete valid plans retain their shape. Update stocks API OpenAPI/types and serializers/Discord consumers in the same PR. The companion solyra plan explicitly owns every existing direct report/persona renderer, including `src/components/insights/ReportCards.tsx`, `src/routes/InsightsPage.tsx`, both insight types files and the shared redesigned decision helpers. Those tolerant consumers must be deployed and verified **before** enabling nullable backend responses; schema additions alone are not safe in either deployment order. See §G for the rollout dependency. A legacy report lacking status loads as `unknown` in presentation metadata rather than being inferred ready; it is historical evidence, not retroactively fixed. Input LLM schemas can stay strict where provider compatibility requires it, but failed/generated values cannot leak into final financial output.

Preserve the existing regime/threshold selection; do not optimize distance rules in this repair. The IWM fixture is a required pending case. Conditional invalidation prose is not itself an assertion that it occurred. Keep production fixtures separate from legacy compatibility fixtures; directly constructing an invalidated output cannot satisfy production coverage. Do not invent trading thresholds or monitoring to fill this absent rule. Flat/blocked plans use `not_applicable`; explicitly include existing conservative-persona weak-FTFC and long-below-200-SMA refusal branches in compute_persona_plans. Tests execute both real planner branches with unchanged existing thresholds and compare a normal ready control; a preconstructed not_applicable fixture is insufficient. Other personas retain their independently valid states; missing price/ATR/source inputs and compute failures use `unavailable`.

`pending_plan(*, persona: str, regime: str, reason: str, candidate_trigger: float | None, confirmation_requirement: str) -> PersonaPlan` does not manufacture bracketing prices or zero-valued financial fields. This repair does not add an ORB-monitoring service: only an existing production observation satisfying the established confirmation path may later support a newly generated ready plan. Source cutoff controls apply before every confirmation observation. Pending never auto-upgrades because wall-clock time passed.

### D. Failure, persistence and API contract

A trader, portfolio manager or deterministic planner failure has a named `failed_sections` entry and canonical public `failed_section_reasons` mapping, source timestamps and a persisted degraded completion outcome. Keep the existing `insight_runs.status`/API `RunState` enum `queued|running|done|failed` for backward-safe polling. Add nullable persisted/API `completion_status=complete|degraded`, immutable `report_version_id` and `failed_section_reasons` (canonical gcp/schema.sql and all three writers). The terminal contract is `(status=done, completion_status=degraded)` when a usable partial report commits with failed required roles/sections, including rejected/mutated risk review; a complete committed report is `(done, complete)`. Missing historical completion metadata remains unknown, never inferred complete from done. Queued/running have no terminal completion outcome; failed means no usable committed version was recovered, with actual error diagnostics. Write completion outcome/reasons and version reference with the run terminal update, deriving them from the durable report. No new terminal status literal is introduced: existing solyra useInsights/InsightsPage pollers continue stopping on done/failed, while report consumers already own the source/failed-section presentation and use the additive outcome when present. Tests replay their existing polling contract and assert GET /api/insights/runs/{run_id} metadata alongside latest/by-ID/history for all three writer paths; legacy clients ignoring optional fields still terminate without treating a new unknown status as running. Record process completion separately from report health. Eliminate final-price fallback to PM output when deterministic planning fails. The response can still carry valid other report sections, but the plan is unavailable and the API cannot label it ready. Distinguish computation failure from a valid flat decision. Integrate via `gcp/insight_pipeline_job.py`, `platform/api/routers/insights.py`, `platform/api/schemas.py`, `lib/agents/schema.py`, `gcp/insight_discord_push.py` and existing report persistence helpers. Expose existing stored `run_kind` truthfully when available; unknown remains unknown.

Consume the receipt/freshness metadata established by `2026-10-12-feat-data-001-data-integrity.md`. The report's generation time is separate from evidence observed/available times; no report becomes current just by being regenerated. API tests cover latest, by-id and history, persisted JSON round trips, failed roles, old rows without new keys, complete plans and all four non-ready statuses at headline and persona levels through latest/by-id/history and Discord, including stale draft prices on invalidated/blocked decisions. Tests must assert the serialized executable fields are absent/null/empty even when the UI is not involved. Guard auth and owner-scoped read behavior with existing tests.

**Failure reason boundary.** Introduce `capture_failure(stage: FailureStage, exc: Exception, *, code: FailureCode) -> FailureRecord` in report_consistency.py. FailureRecord contains public_reason (bounded128-character `stage:error_class:stable_code` composed only from schema allowlists) and optional separately stored operator_diagnostic (≤1024 bytes). Stages are the configured role/section IDs; error_class is allowlisted timeout, transport, schema, dependency, planner, persistence, cancellation or internal; unknown exception classes map to internal. Stable codes include role_timeout, provider_unavailable, schema_invalid, source_unavailable, planner_failed, persistence_failed, generation_deadline, risk_review_incomplete and risk_plan_mismatch. Invalid/unknown code uses internal_error, never the exception's arbitrary class/message. The public failed_section_reasons map is section→public_reason, constructed at capture and round-tripped unchanged; failed_sections still lists actual failed sections. Diagnostic detail does not replace this public contract.

Apply the same explicit redactor before any optional operator persistence/log/transport: discard Authorization/Cookie/API-key/token/password/secret values, credential-bearing URLs (userinfo and query), connection strings/DSNs, SQL statement parameters, request/response headers/bodies and control-character/stacktrace content. Optional operator diagnostics carry only this redacted bounded context; raw str(exc)/repr(exc), logger.exception traceback chains or provider request text cannot reach uncontrolled logs on these handled report failure paths. No secret retrieval is needed. Fixtures inject dummy bearer/key/password/DSN/query/header/SQL values into exceptions, assert absent from DB public/operator columns, API, Discord and captured logs, and assert exact public mapping equality through job/API/historical writers and /runs. Scope is report failure boundaries, not a repository-wide logging rewrite.

### F. Immutable versions and positive historical selection (review C2–C3)

Append the immutable version, update an allowed `insight_reports` cache/pointer AND apply the fenced terminal done transition with complete/degraded metadata in one transaction, replacing the existing final _upsert_report network roundtrip; append history even when current-pointer update is intentionally skipped. Idempotency is `(run_id,ticker,as_of)` with identical payload/hash; a direct conflicting write under that identity fails explicitly. At claim/resume, all three job/API/historical paths first look up a committed version under that identity before provider/model generation. If found, verify its immutable hash, restore any permitted current pointer and finalize any legacy/interrupted terminal state from its stored outcome/reasons within the same claim/recovery transaction without rerunning the nondeterministic pipeline or allocating another version. A lost commit acknowledgement or a legacy incomplete run-status transition cannot strand a durable report; new successful version and terminal state publication is atomic as below. There is no existing recoverable lease: add canonical insight_runs owner_token (opaque per claimant), claim_epoch (monotonic bigint) and lease_expires_at (aware DB timestamp), with `claim_run(run_id, owner_token) -> RunLease | None` and `transition_run(run_id, *, lease: RunLease, status, outcome, version_id, public_reasons) -> bool`; the explicit lease is also required by persist_report_version and capture_bundle_versions. DB-clock CAS claims queued or reclaimable failed/expired-running attempts, increments epoch and sets a fixed1860-second expiry; unexpired ownership is never stolen, even if status is failed. First ownership of an unleased queued/failed attempt is explicit; no ambiguous legacy running lease is guessed active/current—operator disposition or verified expiry policy is recorded. Enforce <=1800-second hard logical-generation deadline in all three entrypoints, including actual provider/transport waits and cancellation; no timeout increase or automatic renewal/heartbeat queries. Deadline exhaustion cancels generation, rejects late output and records failed/degraded using only already committed usable output. Fence every section/version/pointer and terminal write by matching run_id+owner_token+claim_epoch and DB now<lease_expires_at in the same short transaction, serializing against claim takeover by locking/guarding the insight_runs row; use current database clock after lock acquisition, not a cached process or transaction-start timestamp. No external I/O occurs while holding the fence. Bound SQL lock/statement/transaction time by remaining lease/deadline and reject late results before commit; concurrent claim/publication tests prove takeover and old-owner writes cannot both succeed. This prevents a timed-out or replaced owner from publishing. A fenced owner may read committed evidence but cannot mutate it. Normal successful generation on all three paths has exactly three persistence network phases: (1) atomic create/claim plus committed-version recovery lookup; (2) one batched pre-model selected-input/reflection snapshot write; (3) the existing final upsert replacement transaction containing immutable append, allowed current pointer AND fenced done/complete-or-degraded metadata. Thus historical's existing one final write gains at most two roundtrips; no separate successful terminal network call follows publication. Batch receipt/version reads into the already necessary source/bundle reads; any extra lookup must fit this same total, not another allowance. Use one server transaction/call per phase with parameters and server-side row fencing, not BEGIN/COMMIT counted as free client trips. I/O-shape tests instrument actual driver calls/transactions for job, API fallback and historical generation, including section/reflection capture and provenance. Inject terminal-done failure inside final transaction: version and pointer roll back together.
