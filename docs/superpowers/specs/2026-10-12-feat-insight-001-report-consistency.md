# Report consistency and explicit pending trade plans

## Approval and scope

Approved repair scope: [GCP repair review](https://chatgpt.com/space/page_531ea2540b4c8191a4e5267eb24f1b89). On 2026-10-12 the user directed, “Execute the plan with test driven development.” This spec records that previously approved repair scope; it does not claim fresh approval of additional features. Approval covers implementation and tests of these repairs, not an assertion that a provider credential or unverified endpoint works. Spec publication precedes implementation.

## Problem

The reviewed production IWM report says a strong directional thesis while its final deterministic conviction is low. `lib/agents/orchestrator.py` calibrates conviction and replaces numeric plans after the portfolio-manager narrative has already been written. Its planner failure branch still copies LLM prices; trader/manager failures also synthesize confidence. The October 8 fixture uses close 277.7, ATR 3.7368433430628203 and a distant previous-year trigger 171.73, yet presents entry/stop/targets as an actionable plan while its rationale asks for ORB confirmation. These are reproducible contract inconsistencies, not evidence that a new trading strategy works.

Evidence: the approved review, `work/gcp-review/planner-reproduction.json`, `deep-results.json` and the inspected report API schema/handler (protected endpoint probes returned 403; a current authenticated payload was not independently verified), based on stocks `17bbacd371843963a3d7983589ffc8c825664675`. Promote sanitized fixture excerpts into tests during implementation. Catalog row: `FEAT-INSIGHT-001 | AI insights | LLM per-ticker reports + chat`. Touches stocks#1295 (failed trader/manager output); the broader stocks#1217 replay defect is a dependency/context, not a claim this limited spec closes every replay path. The data integrity spec supplies source metadata; this spec consumes it after publication without editing that spec or catalog capability definitions.

## Non-goals

No calibration-threshold retuning, new entry strategy, forced bullish/bearish interpretation, model promotion, report-history rewrite, or unrelated chat overhaul. Do not turn a failure into a neutral recommendation. Do not claim that a generated confidence score is a measured probability. Preserve valid existing deterministic recipes; repair the publication contract.

## Approaches considered

1. Prompt-only warnings: rejected because post-generation calibration still changes the published decision.
2. Replace the planner or retune thresholds: rejected; the approved issue is truthful representation of known deterministic output.
3. Finalize deterministic decision facts before publication, constrain the narrative to them and represent pending/unavailable plans explicitly: selected.

## Design

### A. Final decision contract

Add `lib/agents/report_consistency.py` with `DecisionFacts` (final direction, calibrated conviction, nullable model confidence, confidence provenance, plan state, deterministic plan, source receipt references, failed sections and reasons). `finalize_decision(*, direction: str, conviction: str, confidence_score: float | None, plans: list[PersonaPlan], failed_sections: list[str], source_status: list[dict]) -> DecisionFacts` composes final facts without inventing financial values. Keep the existing `_calibrate_conviction` rules and thresholds. Missing calibration inputs remain unavailable and are recorded; never substitute FTFC 0 or synthetic confidence 0.3 merely to make calibration succeed. Expose nullable `calibrated_conviction` and `conviction_status=unavailable` for unknown calibration. Widen final `conviction` to nullable rather than storing an invented low/neutral placeholder; legacy complete reports retain their original enum values.

Update `lib/agents/schema.py` with additive `plan_status` (`ready|pending_confirmation|invalidated|unavailable|not_applicable`), `plan_reason`, `confirmation_requirement`, nullable `candidate_trigger` (context only), `invalidation_observation` (rule identity and observation time), `conviction_status`, `decision_provenance`, `confidence_kind` (`model_score|unavailable`) and source-health metadata on final reports/persona plans. No field promises a calibrated probability. Keep existing route names and valid-response field names. For pending/unavailable plans, widen final output `entry_zone` and `stop` to nullable, leave targets empty, and make sizing/risk metrics nullable when not meaningful. This is an explicit schema widening needed to remove fabricated prices; complete valid plans retain their shape. Update stocks API OpenAPI/types and serializers/Discord consumers in the same PR. The companion solyra plan explicitly owns every existing direct report/persona renderer, including `src/components/insights/ReportCards.tsx`, `src/routes/InsightsPage.tsx`, both insight types files and the shared redesigned decision helpers. Those tolerant consumers must be deployed and verified **before** enabling nullable backend responses; schema additions alone are not safe in either deployment order. See §G for the rollout dependency. A legacy report lacking status loads as `unknown` in presentation metadata rather than being inferred ready; it is historical evidence, not retroactively fixed. Input LLM schemas can stay strict where provider compatibility requires it, but failed/generated values cannot leak into final financial output.

### B. Pending confirmation semantics

Extend `lib/agents/trade_planner.py::compute_persona_plans` and `_orb_only_plan` so an `orb_only` or `extended` regime that requires a not-yet-observed 15-minute opening-range confirmation returns `pending_confirmation`, a reason and a structural candidate reference, with no executable entry/stop/targets. Preserve the existing regime/threshold selection; do not optimize distance rules in this repair. The IWM fixture is a required pending case. Its 171.73 historical reference may remain in `key_levels` with source/time and label; it cannot become a current executable entry. Keep `ready` for normal, complete, allowed plans. An existing sourced invalidation condition that is already met produces `invalidated` with the condition identity and observation time; this is distinct from pending activation and does not introduce new trading thresholds or monitoring. Flat/blocked plans use `not_applicable`; missing price/ATR/source inputs and compute failures use `unavailable`.

`pending_plan(*, persona: str, regime: str, reason: str, candidate_trigger: float | None, confirmation_requirement: str) -> PersonaPlan` does not manufacture bracketing prices or zero-valued financial fields. This repair does not add an ORB-monitoring service: only an existing production observation satisfying the established confirmation path may later support a newly generated ready plan. Source cutoff controls apply before every confirmation observation. Pending never auto-upgrades because wall-clock time passed.

### C. Narrative reconciliation

Modify `lib/agents/orchestrator.py` so final deterministic facts are settled before final report prose is published. `reconcile_narrative(draft: NarrativeDraft, facts: DecisionFacts) -> NarrativeResult` in `report_consistency.py` accepts only structured claims tied to the final decision and supplied source identities. The narrative schema separates sourced facts, conditional bull/bear scenarios and final decision summary. Preserve scenarios as conditional arguments; a bear argument can exist under a low-conviction long decision, but cannot be presented as the final recommendation. Build the short final decision/plan summary deterministically from final direction, conviction availability and plan state. Update `lib/agents/prompts.py` and existing structured-output validation to identify draft interpretation versus authoritative facts.

Validate structured direction/conviction/plan claims against `DecisionFacts` and source numeric values. Contradictory or unverified recommendation prose is withheld with an explicit narrative consistency reason; do not regex-rewrite random numbers or claim a regex catches all semantic contradictions. Retain verified source facts and clearly conditional scenarios. No extra LLM call is required: pass final facts into existing final synthesis where ordering permits, and fail a conflicting section explicitly otherwise. Store original draft only as auditable diagnostic interpretation, never as the final actionable thesis. Confidence remains the supplied model score only when valid and identified as such; absence is null. Regression fixtures include `LLM high -> calibrated low`, risk block -> flat, opposite scenario text, fabricated stop, and missing FTFC.

### D. Failure, persistence and API contract

A trader, portfolio manager or deterministic planner failure has a named `failed_sections` entry and reason, source timestamps and a run terminal state reflecting degradation. Eliminate final-price fallback to PM output when deterministic planning fails. The response can still carry valid other report sections, but the plan is unavailable and the API cannot label it ready. Distinguish computation failure from a valid flat decision. Integrate via `gcp/insight_pipeline_job.py`, `platform/api/routers/insights.py`, `platform/api/schemas.py`, `lib/agents/schema.py`, `gcp/insight_discord_push.py` and existing report persistence helpers. Expose existing stored `run_kind` truthfully when available; unknown remains unknown.

Consume the receipt/freshness metadata established by `2026-10-12-feat-data-001-data-integrity.md`. The report's generation time is separate from evidence observed/available times; no report becomes current just by being regenerated. API tests cover latest, by-id and history, persisted JSON round trips, failed roles, old rows without new keys, complete plans and pending/unavailable nullability. Guard auth and owner-scoped read behavior with existing tests.

### E. Acceptance, capacity and delivery

Use production `run_insight_pipeline` and `INSIGHT_AS_OF` execution with injected provider/DB fixtures. Assert persisted report JSON and actual API responses, not only helper outputs. Report replay excludes later availability/revisions and cannot consume repaired chains as if known on October 8. Positive fixture proves unchanged normal deterministic plans; negative fixtures prove no fabricated LLM fallback fields, conviction contradiction or pending numerical entry. Stock API tests constitute in-PR proof; owner-run deployed-site checks after staging deployment are separate close-out evidence, not boxes ticked by a hermetic frontend mock.

Volume: one existing report payload per ticker, at most 100 KB bounded structured source/claim metadata; no full chain rows added to report JSON. Velocity: no additional external LLM calls, no per-claim SQL; at most one existing report upsert plus a batched receipt lookup for all source references. Wall-clock: ≤2 extra pg8000 round-trips ×2 s + ≤0.1 s validation = **4.1 s incremental per ticker**; for three tickers ≤12.3 s, measured against the configured job timeout/4 along with the existing pipeline runtime (reviewed run ≈161 s). Cost: at the observed 1-vCPU/4-GiB allocation, incremental ≤12.3 s ×($0.000024 +4×$0.0000025) ≈$0.00042/run, ≈$0.0126 per 30 daily runs; existing LLM usage and baseline job cost are unchanged estimates, not new promises. If final synthesis requires another LLM call, that violates this plan's capacity assumptions and must be resolved before implementation is claimed complete. I/O-shape tests enforce the limits; no timeout increase.

The implementation runbook lists redacted fixture provenance, schema compatibility and null handling, exact API assertions, dry-run pipeline invocation, source-health alert integration and rollback to the previous image with additive schema retained. Immutable report attempts are never rewritten; `insight_reports` may remain a mutable current pointer/cache, while corrected reports append an independently addressable history version as §F defines. Before ready review, update only the owning FEAT-INSIGHT-001 catalog record and traceability entry; run docs audit against origin/main and the delivery gate.

### F. Immutable versions and positive historical selection (review C2–C3)

Reuse `insight_reports_history` (existing BIGSERIAL `id`, `insight_run_id`, `as_of`, `written_at`, `report`, operational run_kind). The report implementation owns additive changes in canonical `gcp/schema.sql`, applied through existing `gcp/apply_schema.py` before API readers, plus companion `gcp/queries/insight_report_versions.sql` and `lib/agents/report_versions.py`; do not add an unrelated parallel history table. `persist_report_version(report: InsightReport, *, run_id: str, generation_kind: str, operation_kind: str, generated_at: datetime, source_versions: list[EvidenceVersionRef]) -> ReportVersion` is shared by the job writer and API background/synchronous fallback writer. Append the immutable version and update an allowed `insight_reports` cache/pointer in one transaction; append history even when current-pointer update is intentionally skipped. Idempotency is `(run_id,ticker,as_of)` with identical payload/hash; a retry with different content under that identity fails explicitly. Different run IDs at the same ticker/cutoff always append different versions. Replace the incidental unique `(ticker,as_of,written_at)` constraint if necessary to permit distinct concurrent attempts; do not let equal wall-clock timestamps collapse them. Preserve all existing history rows.

Public `version_id` is `history:<BIGSERIAL id>`; `current_report_id` is the existing mutable UUID or null when unlinked; `run_id` identifies the attempt. `as_of`/`data_cutoff` is the data boundary, `generated_at` is actual completion time and `available_at` is first successful commit of that exact serialized version. Keep recorded `written_at`; it does not retroactively establish source availability. Store payload hash, the §M shared `temporal_proof`, full source-version dependencies and excluded sections. Normalize new `generation_kind` to `live|replay|backfill` from explicit execution context and retain old operational kind (`scheduled`, `manual_update`, `replay_refresh`, etc.) separately as `operation_kind`. Do not infer provenance for ambiguous legacy rows; expose unknown and unproven.

Extend existing routes without breaking default legacy current/history clients:

- `GET /api/insights/report/{ticker}` without selectors retains current-cache behavior. With aware `as_of`, use `select_report_version(ticker: str, *, cutoff: datetime, version_id: str | None = None) -> ReportVersion | None` against immutable history, requiring known availability and all included dependency observations/versions eligible before the cutoff.
- `GET /api/insights/report/{ticker}/history?versions=true&as_of=<aware ISO>&limit=20` uses `list_report_versions(ticker: str, *, cutoff: datetime | None, limit: int) -> list[ReportVersionSummary]`. SQL filters **before** ordering/limit; order by available_at DESC, id DESC. `versions=true` is explicit opt-in; default legacy history shape/behavior is retained and documented as current-cache rows, not immutable attempts. Version entries use `id=version_id`, optional current_report_id, run ID, both cutoff/generated/available clocks, normalized generation_kind and original operation_kind, proof, nullable decision fields and a bounded decision projection (direction, conviction, confidence provenance, plan state/entry/stop/targets/reasons, source revisions). No N+1 full-report fetch is required to compare two versions.
- `GET /api/insights/reports/{report_id}` continues accepting current UUIDs; an added `history:<positive integer>` identifier selects the exact immutable payload. Optional `as_of` enforces eligibility before returning it. The response identifies `record_kind=history_version` versus `current_cache`; callers cannot mistake one for the other. The same ticker/version is addressable through the selected-report helper. No unrelated new endpoint is needed.

For the production bundle, consume data spec §M and assign every existing section before model invocation: options/gamma/catalysts/ETF fields use the data-owned version selectors; market/STRAT/backtest/sentiment use stored typed input-section snapshots captured by `capture_bundle_versions(bundle: dict, *, run_id: str, captured_at: datetime) -> list[EvidenceVersionRef]` in `lib/agents/evidence_snapshots.py`. Capture complete immutable selected payloads on eligible live collection, with field-covered observed bounds, availability at capture and source hashes. `select_replay_bundle(ticker: str, *, cutoff: datetime) -> dict` reads those persisted versions; no snapshot/proof means unavailable section, and no legacy date-only source query may refill it. In particular, current same-date premarket fields, revised backtest labels, unversioned news/8-K records and later sentiment cannot enter replay. Retain the existing exclusion of self-referential signal history. Proven macro-only historical evidence can still produce a degraded report with unavailable plan/other sections; do not invent missing market data to make it actionable.

The positive same-cutoff fixture executes the production writer twice for ticker IWM and data_cutoff `2026-10-08T13:00:00Z`, with distinct run IDs and generated/available times 14:00 and 15:00 UTC, using actual persisted eligible input-section snapshots. Each run has a different sourced decision projection, and both immutable payloads remain addressable even if the current pointer chooses the second. Research at 16:00 accepts both; research at 14:30 accepts only the first; research at 13:00 accepts neither not-yet-generated report. Add ≥21 later versions and prove the 14:30 SQL query still returns the first (filter before LIMIT). Capture actual API JSON into hashed cross-repository fixtures consumed by the research helper. Another fixture mutates a same-date market/premarket row after cutoff and verifies replay uses the original persisted section or explicitly excludes it, never the changed mutable row.

### G. Compatibility deployment dependency (review C1)

The backend schema change cannot safely precede tolerant financial renderers. The companion solyra Task 6 must make `ReportCards.tsx` headline/persona entry, stop, size, confidence and conviction paths null/status-aware, and exercise `InsightsPage.tsx` plus shared `/insights-lovable` and `/ai-insights-lovable` consumers. Null confidence displays unavailable, never `0%`; pending and invalidated plans never display executable entry placeholders. Legacy complete reports still render their exact financial values. Required browser/API contract fixtures include pending, unavailable, invalidated, null-confidence/null-conviction and complete legacy reports; avoid coercion before formatting.

Release order: merge reviewed data/source contract; implement report repair from that merged base without stacked PRs. The report implementation PR carries schema/tests, but production publication of nullable outputs is blocked until the tolerant solyra consumer commit is deployed and its owner post-staging check is recorded. Because stocks deploys from main, do not merge the nullable-response backend PR before that frontend deployment evidence, unless an explicitly tested opt-in response capability is implemented instead; the chosen routine resolution here is tolerant UI first. Solyra's research adapters can tolerate old backend metadata while waiting, so this ordering does not require invented backend values. Rollback backend to old complete shapes is safe for tolerant UI; do not roll back the UI to unsafe dereferences while nullable responses remain enabled.

Volume adjustment: capture at most seven typed section versions per report in one batch, ≤100KB aggregate selected-section payload, plus the existing ≤100KB report/projection, so ≤200KB persisted payload per ticker/run. Missing/oversized sections remain unavailable; no full chains enter a section. Capacity adjustment for immutable history: one history append plus optional current-pointer update in the same transaction, at most one batched dependency-version read, and one bounded history SELECT. This replaces the existing separated writes where present rather than creating per-claim I/O. Keep the ≤2 additional round-trip/report bound and ≤100KB report/projection budget; assert it against both job and API fallback paths. An index beginning with ticker and known available_at (plus ID tiebreak) bounds the historical selection; no full report scan or per-version fetch is allowed for the 20-row research comparison.

## Risks

Nullable output fields may uncover assumptions in legacy renderers; schema and serializer regressions plus API consumer fixtures must cover them. Deterministic summary alone cannot guarantee arbitrary prose consistency, so unverified final recommendation prose is withheld. Pending state must remain distinguishable from missing-data failure. Source repairs arriving later must not rewrite historical confidence or report evidence. Existing numerical recipes are preserved only for plans actually marked ready.
