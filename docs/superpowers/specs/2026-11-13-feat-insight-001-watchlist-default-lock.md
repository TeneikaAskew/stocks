# Lock the default watchlist to Discord and the CLI; the web reads it and never writes it

## Authority and status

Draft, written 2026-11-13 from the owner's request of the same day: "Default list = SPY, QQQ, IWM.
Only Discord (and the CLI) can change it. Every job keeps reading only 'default'. Solyra reads the
default list read-only and cannot add or remove anything in it. Solyra gets its own per-user
watchlist saved to a table keyed by the user's account. Per-user lists never feed the stocks jobs.
Move the user-facing watchlist to solyra; keep the jobs, Discord and the default list in stocks."

This spec is the stocks half. The solyra half is
`docs/superpowers/specs/2026-11-13-feat-insight-001-user-watchlist.md` in TeneikaAskew/solyra.
Neither is self-approved: `status` moves to `approved` only when the owner merges this spec PR.
No code changes before that.

## Problem

Read in the code at origin/main 61bbd17 and in production on 2026-11-13 (read-only query through
`scripts/db_query_cr.sh`, execution db-query-km4qh, rolled back).

1. **One table, two kinds of owner, and only one is read.** `watchlists` is keyed by
   `(user_id, ticker)`. Every scheduled job reads `user_id = 'default'` (section Readers). The web
   endpoints in `platform/api/routers/insights.py` scope to the signed-in email through
   `_watchlist_owner` (`:57-67`, `current_user_email(request) or "default"`). So in the deployed
   firebase mode a user's add writes a row no job will ever read (#1261, a symbol a signed-in user
   picks never reaches the nightly signals job), and the ranker behind `GET /api/insights/watchlist`
   ranks that user's own rows, which are empty (#1215, the Watchlist tab is empty for every
   signed-in user except the default owner).
2. **Production holds the default owner only.** The 2026-11-13 read found 18 rows, all
   `user_id = 'default'`: 16 active and 2 removed (MSFT and SPX, removed 2026-04-28 and 04-30).
   Three active rows carry every surface flag, SPY, QQQ and IWM (`in_brief`, `in_insight`,
   `signals` all true, source `seed`, added 2026-04-27). The other 13 active rows carry no flag:
   AVGO (seed), ASTX, NVDA and MCK (source `discord-replay`) and 9 peers added 2026-04-30 with
   source `avgo-peer` (AMD, ANET, ARM, CSCO, MRVL, MU, QCOM, TSM, TXN). `watchlist_history` holds
   only its 20 seed rows (18 add, 2 remove); no trigger-written row exists yet. No email-owned row
   exists, so nothing is lost by moving per-user lists out of this table.
3. **Nothing enforces the rule the owner wants.** In `open` mode (local development, and any
   deployment whose `AUTH_MODE` resolves to open) `_watchlist_owner` returns `'default'`, so a web
   add or remove edits the universe every job reads. In firebase mode it cannot, but only because the
   owner resolves to an email; the lock is an accident of auth mode, not a rule.
4. **One reader ignores removal and ownership.** `gcp/fetchers/fetch_market_data.py:843-845`
   (`_backfill_targets`, the manual `--backfill` path without `BACKFILL_ALL_HISTORY`) selects
   `ticker FROM watchlists WHERE COALESCE(in_brief, false) OR COALESCE(in_insight, false)` with no
   `removed_at IS NULL` and no `user_id` filter. A removed ticker and any owner's rows are backfill
   targets.
5. **The add route fabricates an empty list on a failed read-back** (#1329, `insights.py:639-643`,
   `except Exception: watchlist = []`). Retiring the web write path removes the fabrication.

## Non-goals

- No change to the Discord `/watchlist add`, `remove` and `list` subcommands or their flags; they
  stay the way the default list changes. No `signals` option is added here.
- No change to which owner any job reads or to any job's surface filter. The inventory below is
  recorded as the contract, not changed.
- No removal of the 13 unflagged default rows. Whether the default list is exactly SPY, QQQ and IWM
  or keeps the research peers is the owner's call, made with `/watchlist remove`, not by code.
- No per-user storage, read or write, in stocks. The per-user list, its table, its endpoints and
  its UI are the solyra spec. Existing email-owned rows do not exist, so no migration moves data.
- No deletion of market, news, options or history data when a ticker leaves the list, now or
  later. Removal stays a soft delete that the history trigger records.
- No change to these behaviours, each named here so the owner can decide separately: the signal
  monitor reads its list once at startup (`gcp/signal_monitor.py:297-316`); the insight analog
  universe counts a ticker removed today for the rest of today and for every replay dated before
  the removal (`gcp/fetchers/_watchlist.py` `resolve_membership_at`); the earnings-history chain
  keeps refreshing every ticker ever pulled (`gcp/fetchers/fetch_earnings_history.py:373, 558-559`);
  `backfill-ticker`, dispatched by Discord `/replay` for a ticker with no daily data, re-activates a
  removed default row (`gcp/backfill_ticker.py:328-332`, `BACKFILL_ADD_TO_WATCHLIST` default true);
  a re-add restores the flags the row had when it was removed.
- No removal of the two web write routes from the router in this change. They stay declared and
  answer 410 so solyra's contract test keeps passing until solyra stops calling them; deleting
  them is its own small spec once solyra's change is on main.

## Approaches considered

1. Keep per-user rows in `watchlists` keyed by email and only lock `'default'`. Rejected: the owner
   moved the user-facing list to solyra; jobs never read per-user rows anyway; and one table with two
   writers (web and Discord) is the ambiguity that produced #1215 and #1261.
2. Delete the two write routes now. Rejected for ordering: solyra still calls them from
   `TickerCombobox` and the Watchlist tab, and `src/mocks/contract.test.ts` fails the moment an
   operation the app requests leaves the OpenAPI document. A 410 keeps the operation declared and
   gives the UI an honest error until solyra's change lands.
3. Chosen: every web write answers 410 and writes nothing; one new read-only endpoint serves the
   default list with its flags; the ranker is pinned to `'default'` for every caller and keeps
   `extras` for per-call tickers; the one reader that ignored removal and ownership is fixed; a
   source-scan test keeps every reader on `'default'`.

## Design

### Owners and writers

`watchlists.user_id = 'default'` is the only owner stocks reads or writes from now on.

| Writer | Path | Allowed after this change |
|---|---|---|
| Discord `/watchlist add` (flags `brief:`, `insight:`), `/watchlist remove` | `gcp/discord_interactions/main.py:599-700`, `WATCHLIST_USER_ID = "default"` | yes, unchanged |
| `backfill-ticker` job, dispatched by Discord `/replay` when a ticker has no daily data | `gcp/backfill_ticker.py:328-332`, source `discord-replay` | yes, unchanged (named above as a decision for the owner) |
| CLI: operator SQL through `scripts/db_query_cr.sh --commit`, and the schema seed | `gcp/schema.sql:2502-2532` (`signals` seed for IWM, QQQ, SPY) | yes, unchanged |
| Web `POST /api/insights/watchlist/add`, `DELETE /api/insights/watchlist/{ticker}` | `platform/api/routers/insights.py:599-700` | no: both answer 410 Gone, detail `The watchlist is managed in Discord (/watchlist add, /watchlist remove); the web app keeps per-user lists in solyra.` They import nothing from `gcp.fetchers._watchlist` any more, so no write can reach the table from the API process. |

`_watchlist_owner` is deleted. No endpoint in the API resolves a watchlist owner from the request
any more; every read names `'default'` in code. That makes the rule hold in every auth mode, which
is what REQ-TENANCY-001 asks of an owner key: fixed and enforced on every access path, not derived
from who is calling.

### New read-only endpoint

`GET /api/insights/watchlist/default`, response model `WatchlistDefaultResponse` in
`platform/api/schemas.py`:

```
as_of: str            # ISO instant the query ran, UTC
owner: "default"
rows: list[WatchlistDefaultRow]
```

`WatchlistDefaultRow`: `ticker: str`, `in_brief: bool`, `in_insight: bool`, `signals: bool`,
`source: Optional[str]`, `added_at: str`. Query, through the strict function
`gcp.database.query_to_dataframe` (the one `gcp/calibrate_level_params.py:96-100` uses for the same
reason, a failed read must not become an empty list):

```
SELECT ticker, in_brief, in_insight, signals, source, added_at
  FROM watchlists
 WHERE user_id = 'default' AND removed_at IS NULL
 ORDER BY added_at, ticker
```

A database error answers 503 with the exception text in `detail` (REQ-DATA-001, EXTERNAL failure
surfaced, never an empty list). The endpoint is gated like the rest of `/api/insights` (REQ-AUTH-001);
it is not added to `_OPEN_API_PREFIXES`. Capacity: one indexed read (`idx_watchlists_active`) of 16
rows per call, no new job, no new scheduler.

### Ranked list

`GET /api/insights/watchlist` keeps its contract and calls `rank_tickers(..., user_id="default")`.
`extras` keeps injecting per-call tickers as `manual` candidates
(`lib/agents/ranker/candidates.py:299-310`); that is the hook solyra uses to rank a user's own
tickers beside the default list without stocks storing them. `expand` is unchanged.

### The one reader fix

`gcp/fetchers/fetch_market_data.py` `_backfill_targets`: the `watchlists` branch becomes
`SELECT ticker FROM watchlists WHERE user_id = 'default' AND removed_at IS NULL AND (in_brief OR in_insight)`.
It runs only on the manual `--backfill` path; the scheduled chain sets `BACKFILL_ALL_HISTORY=true`
(`gcp/deploy.sh:2981`) and never reaches it, so no job's wall-clock changes.

### Readers (the contract: every job reads only 'default')

is `SELECT ticker FROM watchlists WHERE user_id = %s AND removed_at IS NULL` plus a surface
predicate (`in_brief`, `in_insight` or `signals` = TRUE). For owner `'default'` it falls through to
the `INSIGHT_TICKERS` env var and then to an empty list with a Discord alert; a failed query also
returns an empty list (`:363-365, 378-380`), which is why the strict callers below bypass it.

What leaves with a ticker: nothing but its membership. No reader deletes data; `removed_at` is set,
the `trg_watchlists_membership` trigger appends a `remove` row to the append-only
`watchlist_history`, and the surface flags stay on the row, so a later re-add (Discord, or
`backfill-ticker` through `/replay`) brings the old flags back.

## Cross-repo contract

| Store | Table | Writers | Readers |
|---|---|---|---|
| stocks Cloud SQL | `watchlists`, rows with `user_id = 'default'` | Discord `/watchlist`, `backfill-ticker` via `/replay`, operator SQL, schema seed | every job in the inventory; `GET /api/insights/watchlist`; `GET /api/insights/watchlist/default` |
| stocks Cloud SQL | `watchlist_history` | the membership trigger only | insight analog universe (`resolve_membership_at`) |
| solyra Supabase project `hajmcfkqmtgidstpggrh` | `user_watchlists` (solyra spec) | the `user-watchlist` edge function on behalf of the signed-in user | the same function for the solyra UI; never a stocks job |

Ordering: this spec's implementation merges first and regenerates `platform/api/openapi.json`;
solyra then runs `npm run contract:sync`, stops calling the two write routes, consumes
`GET /api/insights/watchlist/default` and passes its per-user tickers as `extras`. Until solyra's
change lands, the web app's add and remove show the 410 detail as an honest error (solyra Rule 4),
and nothing is written anywhere.

## Risks

- A deployment in `open` mode today lets the web edit the default list; after this change it cannot.
  If an operator relied on the web add in open mode to curate the list, they use Discord or SQL.
  The 410 detail says so.
- Solyra's `TickerCombobox` auto-adds a new ticker to the watchlist so data ingest follows; after
  this change the stocks side no longer ingests a ticker a web user picks. That is the owner's
  decision (per-user lists never feed the jobs), recorded here so the solyra UI can say "no data yet"
  instead of implying ingest. `done_when` item 1 proves the write path is closed.
- The source-scan test is only as complete as the inventory. It lists the 24 reader and writer
  sites above; a reader added later through a new helper name would need the test extended, and
  review of any new `watchlists` query is the guard for that.
