# Deploy completion-gated data refresh and bounded postrelease actuals

## Approval and scheduling prerequisite

The user approved the [GCP repair review](https://chatgpt.com/space/page_531ea2540b4c8191a4e5267eb24f1b89) and on 2026-10-12 requested, “Execute the plan with test driven development.” This is a capability-ownership split of the approved completion-gated refresh and after-release actuals repair, not additional product scope. FEAT-DEPLOY-001 owns deploy scripts/configuration; the companion FEAT-DATA-001 owns runtime financial/source logic.

The [canonical six-issue candidate inventory](https://github.com/TeneikaAskew/stocks/blob/main/docs/product/12-PR-ISSUE-TRACEABILITY.md#gcp-repair-scheduling-pass-2026-10-12) must publish from its separate docs branch before this approved-scope specification is accepted/published or implementation is scheduled. Record its merged revision in controller preflight. The bounded pass covers #1259/#1260/#1302/#1303/#1365/#1295; this spec touches #1365 only, whose docs-only candidate #1396 is not a runtime fix. This deployment alone does not diagnose or close every cause of the recorded watchdog failure.

## Problem

Reviewed `gcp/deploy.sh` registers `av-options-daily` at 21:00 ET, `gamma-levels-daily` at 22:30 ET and `strat-engine-daily` at 23:35 ET. Elapsed offsets do not establish successful upstream completion or complete source partitions. `economic-events-daily` at 07:00 ET cannot observe later released actuals. The reviewed repair requires actual scheduler wiring; merely adding callable runtime code leaves both failures in production.

## Non-goals

No financial algorithms, provider contracts, history rebuild, trigger/gate governance changes, unrelated job rewiring, new credentials, general workflow engine or automatic issue closure. Do not edit the data/report/research specifications from the implementation branch. Preserve existing monthly options and unrelated STRAT enrichment schedules unless the scoped dependency tests establish that a named duplicate launcher must be disabled and documented.

## Approaches considered

1. Keep fixed offsets: rejected because successful completion is unproven.
2. Replace all workflows: outside the approved scope.
3. Wire the approved runtime orchestrator through existing deployment helpers, disable its duplicate direct launchers and add a bounded due-release dispatcher: selected.

## Design

### A. Ownership, interfaces and merge order

Modify deployment ownership surfaces: `gcp/deploy.sh`, its directly associated deployment/entrypoint/API integration tests and FEAT-DEPLOY-001 documentation. Include scheduler-derived `docs/product/07-MODEL-REGISTRY.md`, `docs/product/generated/model-registry.json` via `scripts/gate/export_model_registry.py`, current scheduler architecture inventory/narrative in `docs/product/infrastructure/05-a-ARCHITECTURE.md` and its maintained manual source `docs/product/infrastructure/manual/05-a-ARCHITECTURE.md`, `docs/STRAT_ENGINE_ARCHITECTURE.drawio`, and directly affected consistency tests (`tests/meta/test_model_registry_consistency.py`, `tests/gcp/test_strat_engine_scheduler.py`). Do not rewrite unrelated architecture or requirement definitions. API acceptance composes merged DATA handlers; this FEAT does not own new catalyst-router or financial/source implementation. Use existing image/service-account/secret-reference/region helpers and create/update conventions. Do not create another gamma/STRAT implementation or provider adapter. After the data implementation merges, consume its production commands:

- `python -m gcp.data_refresh_sequence scheduled-sequence --phase options-gamma [--dry-run]`: at21:00 ET launch existing `fetch-av-options-backfill`, capture its actual execution ID, wait for successful terminal state and expected complete receipts, then launch/wait for existing `p2-build-gamma-levels`, persist the session manifest and exit. No STRAT or wait for23:00 market collection in this phase.
- `python -m gcp.data_refresh_sequence scheduled-sequence --phase strat [--dry-run]`: at23:35 ET resume that same session manifest; require the recorded options/gamma success **and** a genuine successful23:00 `fetch-market-data` execution with complete required same-session daily/intraday/VIX receipts before bounded dependent `strat-engine`. DATA J owns actual market collector receipt production, dependency versions, coverage and negative-path tests. This phase never relaunches options/gamma or launches an extra market job. Use DATA's separately sealed options_phase_cutoff and strat_phase_cutoff: later market availability is admitted only by the late-phase boundary; the early cutoff/versions are never rewritten or backdated. The market23:30 settle target is planning context, not proof of success. Late market can be polled only within this phase's own60-minute bound; otherwise defer without STRAT. - `python -m gcp.data_refresh_sequence due-macro [--dry-run]`: persisted due releases, at most 3 attempts/event through 60 minutes, ≤3 pages/3,000 rows and ≤6 SQL round-trips/invocation, preserving late/unavailable actual status.

### B. Reproducible configuration

Create/update bounded Cloud Run jobs `data-refresh-sequence` and `economic-actuals-refresh` using the existing production image containing the merged runtime and minimal existing identity/secret references. Commands select the phased scheduled mode or due-macro mode above; arguments are equivalent on create and update, including clearing stale args. Explicit max-retries is 0. Resolve job existence and image revision before enabling scheduler targets; unavailable runtime/image fails dry-run/rollout rather than launching stale code.

Retarget existing `av-options-daily` (`0 21 * * 1-5`, America/New_York) to `data-refresh-sequence` with explicit `--phase options-gamma`; retain its daily cadence and existing selected universe. Retarget existing `strat-engine-daily` (`35 23 * * 1-5`) to the same controller with explicit `--phase strat` using authenticated Cloud Run execution argument overrides, not mutable last-writer-wins job args. Preserve `fetch-market-data-daily` at23:00. The two scheduler request bodies must carry distinct complete argument arrays and correct escaping, tested against actual rendered commands. Explicitly pause/remove `gamma-levels-daily`; the old direct `strat-engine` target is disabled by the retargeting. Repeated deploy must neither restore the direct gamma/STRAT launchers nor drop the phase overrides. This retains early options/gamma availability and late market settlement without making a21:00 controller wait multiple hours. At most two controller dispatches/day use existing daily launch slots; no new unbounded job or extra options collection is introduced. Their jobs remain available to the runtime launcher and explicit bounded manual repair. Retain unrelated schedules and `av-options-monthly`; overlap with another options run must remain lock/receipt safe, and an unrelated run ID must not unlock this sequence. Existing `strat-enrich-daily` is not silently treated as the dependent feature-builder launch; inventory its distinct role in the runbook.

Keep `economic-events-daily` 07:00 ET schedule retrieval. Configure one `economic-actuals-refresh` scheduler at `*/15 8-17 * * 1-5` in `America/New_York`, targeting the identically named job. Configure existing authenticated scheduler-to-job identity consistently with current helpers; no public job endpoint. All target URIs resolve to jobs created by the same configuration. Dry-run emits redacted commands/diffs without changing Cloud resources or resolving secret values into logs.

**IAM preflight, fail closed.** Existing setup grants `roles/run.invoker`, which does not establish execution-read capability; a manually present production `roles/run.developer` binding is not reproducible proof. Choose a read-only effective-permission preflight in the real deploy/setup activation path, with no automatic broad-role grant: verify the configured scheduler identity can invoke the controller including phase argument overrides, and the controller identity can launch each exact child and read its returned execution/operation status. Required capabilities include `run.jobs.run`, `run.jobs.runWithOverrides` where overrides are used, `run.executions.get` and the actual transport's operation-read permission if it polls operations, plus existing job-description access where used. Resolve effective principal/resource permissions through an authenticated supported permission-check mechanism; static role-name matching or testing as the deployer's identity is insufficient. Permission-check unavailable/indeterminate is a failed preflight, not a guessed grant. Record principal, resource, tested permissions, timestamp and redacted proof; denied launch, denied poll or denied override blocks new scheduler activation and emits the exact remediation requirement. Operators provision least privilege through the existing reviewed IAM process; this docs batch performs no IAM writes. Fake configuration tests include fresh setup's invoker-only identity, production-like complete permissions and denied/indeterminate cases. No sequence may depend silently on a manual broad role.

### E. Rollout and rollback

Dry-run first; verify deployed image/runtime availability and exact source schema from the data release. Perform effective IAM preflight before activation. Apply job definitions with all affected launchers paused, compare effective create/update configuration, retarget both daily launchers while paused and deactivate direct gamma before enabling either phase and the due-release schedule. Verify the absence of duplicate direct targets immediately before each enable operation. Cloud Scheduler mutations are not atomic: before any new path is enabled a partial failure may retain only old paths or leave affected dispatch paused; once new paths are enabled no old duplicate may be active. On any rejected mutation abort activation, record the step/config and converge to the known old topology only if all new paths are confirmed paused, or to an explicit all-paused fail-closed state if restoration cannot be proven. Do not falsely claim atomic old-or-new rollback when the rollback gcloud call itself can fail. After failure/retry the invariant is always no simultaneous new-plus-duplicate direct launch, including transient states. Fully active success is the complete phased topology. Never run both new and duplicate direct launchers as a rollout shortcut. The runbook includes a redacted manifest and bounded owner-authorized first execution; documentation preparation performs no deployment or data writes.

Rollback pauses both phase launchers and the macro dispatcher, captures active execution/receipt IDs, and leaves last-good data intact. Restore prior job/config references if required; unsafe fixed-offset downstream schedules remain paused until an operator verifies the relevant upstream receipts or runs a bounded sequence. Do not relabel stale data current or erase failed receipts. Document recovery of interrupted locks and due-release attempt cursors using existing runtime semantics.

## Risks

Repeated deploy could recreate old offsets, create/update divergence could leave stale arguments, DST could miss release windows, and waiting controllers could consume excessive timeout/cost. P1–P5 test/measure these boundaries. Operational checks remain required before declaring the overall repair deployed and healthy. This specification changes neither issue definitions nor catalog capability ownership.
