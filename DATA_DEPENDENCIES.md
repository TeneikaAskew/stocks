## 4. Multi-writer tables (coordination risks)

| Table                | Writers                                                                                                                   | Why a coordination risk                                                                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `market_data_daily`  | `fetch_market_data`, `migrate_to_gcp`, `backfill_watchlist_data`, `deep_backfill_ticker`, `fetch_premarket_refresh`          | Multiple backfill/fetch scripts writing to the same core table. All use `upsert` or conflict handling, so risk is low, but concurrent runs could race. |
| `etf_options_snapshots` | `fetch_av_historical_options`, `fetch_av_realtime_options`, `grid.py`, `compute_spx_greeks`, `validate_track2_live` | Realtime and EOD writers. API vs script writers. All use conflict handling, but logic is distributed.                                                |
| `trades`             | `db_query_job`, `migrate_to_gcp`, `trade_logger`, `backfill_signals`                                                        | `trade_logger` is for live trades, `backfill_signals` for simulated. `migrate_to_gcp` is one-shot. Separation of concerns seems clear.                |
| `journal_entries`    | `journal.py`, `backfill_journal_embeddings`                                                                               | API handles user entries, script backfills embeddings. `UPDATE` vs `INSERT`. Low risk.                                                              |
| `premarket_analysis` | `premarket_brief`, `premarket_playbook_resolver`                                                                          | Both jobs update the same rows. `premarket_playbook_resolver` runs after `premarket_brief`. Coordination is sequential. Risk of partial updates if resolver fails. |
| `insight_reports`    | `insight_pipeline_job`, `insights.py` API, `generate_historical_report`                                                   | Multiple paths to create reports. All use UUIDs and conflict handling. Low risk.                                                                     |
| `insight_runs`       | `auto_refresh_top_n`, `discord_interactions`, `insight_pipeline_job`, `insights.py` API                                     | Many triggers for insight runs. All `INSERT`. Race conditions are possible but unlikely to cause data corruption due to UUIDs.                         |
| `news_sentiment`     | `backfill_ticker`, `fetch_news_sentiment`, `fetch_rss_news`, `backfill_news_sentiment`                                      | Multiple news sources and backfill scripts. All use `upsert`. Potential for conflicting data from different sources if not deduplicated correctly.   |
| `watchlists`         | `backfill_ticker`, `discord_interactions`, `_watchlist.py`, `signal_monitor`                                              | User-facing (Discord) and system jobs writing to watchlists. `UPDATE` vs `INSERT`. Logic is complex and spread out. High potential for subtle bugs.   |
